Database Administration

Core DBA Operations & Architecture
15 Questions
These questions cover the bread-and-butter of daily DBA work — from memory management to undo, redo, ASM, and net configuration. Senior DBAs must answer these without hesitation.
TECHNICAL Checkpoint Types
Q1: Explain Oracle's checkpoint process. What triggers a checkpoint and what are the types?
▼ Show Model Answer

A checkpoint writes all dirty buffers (modified data blocks in the buffer cache) to datafiles, advancing the checkpoint SCN and updating the control file and datafile headers.


TYPES:
• Full Checkpoint: All dirty buffers flushed. Triggered by: shutdown normal/immediate, ALTER SYSTEM CHECKPOINT, log switch (when fast_start_mttr_target=0), tablespace backup.
• Incremental (Thread) Checkpoint: Continuous background process driven by DBWR. Controls crash recovery time via FAST_START_MTTR_TARGET.
• Object-level Checkpoint: Triggered by DROP/TRUNCATE table — all dirty blocks for that object flushed.
• Log Switch Checkpoint: Triggered every time Oracle switches from one redo log group to another.

KEY METRICS: V$INSTANCE_RECOVERY shows current MTTR and I/O factor. High checkpoint frequency = high I/O; tune with FAST_START_MTTR_TARGET and undersized redo logs.

TECHNICAL Undo Management
Q2: How does Oracle Undo work? Explain the difference between UNDO_RETENTION and undo guarantee.
▼ Show Model Answer

Undo records the 'before image' of data for: transaction rollback, read consistency (multi-version concurrency), and Flashback operations.


UNDO_RETENTION: A hint to Oracle to retain undo for at least X seconds. NOT a guarantee — if space is needed for active transactions, old undo can be overwritten. Default: 900 seconds.


UNDO GUARANTEE (RETENTION GUARANTEE): ALTER TABLESPACE undotbs1 RETENTION GUARANTEE — this prevents active transactions from overwriting undo even if it means new DML fails with ORA-30036. Use for environments requiring long Flashback Query windows.


SIZING FORMULA: Undo Size = UNDO_RETENTION × Undo Blocks Generated per Second × DB_BLOCK_SIZE


KEY VIEWS: V$UNDOSTAT (10-minute snapshots of undo activity), V$TRANSACTION (active transactions), DBA_UNDO_EXTENTS.


TUNING: If ORA-01555 (snapshot too old) errors occur: increase UNDO_RETENTION, increase undo tablespace size, or optimize long-running queries that consume undo.

TECHNICAL Redo Log Design
Q3: Walk me through redo log management best practices. How many groups, members, and what size?
▼ Show Model Answer

Redo logs record all changes to the database for instance recovery.


ARCHITECTURE: Groups (logical) → Members (physical files, one per disk for mirroring). Always multiplex members across different disks/controllers.


SIZING GUIDANCE:
• Log switches should happen every 15–30 minutes under normal load (not every 2–3 minutes).
• Too small = excessive log switches = excessive checkpoints = I/O spikes.
• Too large = longer instance recovery time.
• Use V$LOG_HISTORY to check switch frequency per hour.
• Rule of thumb: start at 500MB–2GB for busy OLTP; adjust based on archive generation rate.

GROUP COUNT:
• Minimum 3 groups (so log writer always has a group available while archiver catches up).
• For high-throughput systems: 5–10 groups.
• ADD GROUP: ALTER DATABASE ADD LOGFILE GROUP 4 ('/ora/redo04a.log', '/ora/redo04b.log') SIZE 1G;

MONITORING: V$LOG (current status: CURRENT, ACTIVE, INACTIVE, UNUSED), V$LOGFILE, V$LOG_HISTORY.

ALERT: Alert log will show 'checkpoint not complete' if log switches too fast for DBWR to keep up — add groups or increase size immediately.

TECHNICAL ASM Architecture
Q4: Explain ASM (Automatic Storage Management) — disk groups, failure groups, and AU sizing.
▼ Show Model Answer

ASM is Oracle's integrated volume manager and filesystem for Oracle datafiles, providing striping and mirroring without a third-party volume manager.


DISK GROUPS: Logical pool of physical disks. Redundancy levels:

• EXTERNAL: No ASM mirroring (rely on hardware RAID). Best for Exadata or HW RAID.
• NORMAL: 2-way mirroring (needs ≥2 failure groups). Standard for most environments.
• HIGH: 3-way mirroring (needs ≥3 failure groups). Mission-critical production.

FAILURE GROUPS: Logical grouping of disks that could fail together (same controller, same shelf). ASM mirrors data across failure groups, not just across disks.

Example: 2 SAN controllers → 2 failure groups → NORMAL redundancy ensures one controller failure doesn't lose data.


ALLOCATION UNIT (AU): Smallest unit ASM allocates. Default 1MB; for VLDB or Exadata: 4MB or 8MB AUs improve large sequential I/O. Set at disk group creation (cannot change after).


KEY VIEWS: V$ASM_DISKGROUP, V$ASM_DISK, V$ASM_FILE, V$ASM_OPERATION (rebalance progress).


REBALANCING: ALTER DISKGROUP data REBALANCE POWER 8; — higher power = faster but more I/O impact.

TECHNICAL Shared Pool ORA-04031
Q5: How do you troubleshoot and resolve ORA-04031 (unable to allocate X bytes of shared memory)?
▼ Show Model Answer

ORA-04031 = Oracle cannot find a contiguous chunk of memory in the shared pool (or large pool/java pool) of the requested size.


IMMEDIATE DIAGNOSIS:

1. Check which pool: alert log message identifies shared pool, large pool, or java pool.

2. Query V$SGASTAT WHERE pool = 'shared pool' — look at 'free memory'.

3. Check V$SQL WHERE VERSION_COUNT > 5 — high version counts indicate cursor proliferation from literal SQL.

4. Check V$SHARED_POOL_RESERVED for reserved area exhaustion.


ROOT CAUSES:
• Non-shared SQL (literals instead of bind variables) — fragments the shared pool.
• Shared pool too small for workload.
• JAVA_POOL_SIZE too small (if java pool mentioned).
• Very large PL/SQL packages being loaded/reloaded.

IMMEDIATE REMEDIATION:
• ALTER SYSTEM SET CURSOR_SHARING = FORCE (emergency only; prefer bind variables properly).
• EXECUTE DBMS_SHARED_POOL.KEEP('large_package', 'P') — pin critical objects before startup.
• ALTER SYSTEM SET SHARED_POOL_SIZE = <larger_value> SCOPE=BOTH (if dynamic).
• FLUSH SHARED POOL only as last resort — causes a parse storm.

PREVENTION: Enforce bind variables in application code; use shared_pool_reserved_size (5–10% of shared_pool_size); monitor V$SQL.VERSION_COUNT regularly.

TECHNICAL Lock Management
Q6: Explain Oracle's locking model — row-level locks, table locks, and how to detect/resolve blocking.
▼ Show Model Answer

Oracle uses a multi-version concurrency control (MVCC) model — readers never block writers, writers never block readers.


LOCK TYPES:
• TX (Transaction) Lock: Row-level lock acquired when a row is modified. Held until COMMIT or ROLLBACK. Stored in the block header (no lock table overhead).
• TM (DML) Lock: Table-level lock preventing DDL while DML is in progress. Modes: RS (Row Share), RX (Row Exclusive), S (Share), SX (Share Row Exclusive), X (Exclusive).
• Library Cache Lock/Pin: Protects shared SQL and PL/SQL objects during compilation.
• Enqueue Locks: Named resources (HW — high water mark, ST — space management, TX — transaction).

DETECTING BLOCKING:

SELECT blocker.sid AS blocking_sid, blocker.serial#, blocker.username,

waiter.sid AS waiting_sid, waiter.sql_id, waiter.event

FROM v$session blocker

JOIN v$session waiter ON blocker.sid = waiter.blocking_session

WHERE waiter.blocking_session IS NOT NULL;


RESOLUTION:
• Application level: ensure transactions commit/rollback quickly; short transaction design.
• Emergency: ALTER SYSTEM KILL SESSION 'sid,serial#' IMMEDIATE (kills blocking session).
• Root cause: look for application code that holds locks across user interactions (open transactions).
• Use DBMS_LOCK for application-controlled locking where needed.
TECHNICAL Recycle Bin
Q7: What is the Oracle Recycle Bin and how does it work? When would you disable it?
▼ Show Model Answer

The Recycle Bin is a logical container within each tablespace that retains dropped objects until the tablespace needs space. Objects remain queryable and can be restored with FLASHBACK TABLE.


HOW IT WORKS:
• DROP TABLE t1 → object renamed to BIN$... and moved to recycle bin (no space freed yet).
• Space is reused by Oracle only when the tablespace needs it (oldest objects purged first).
• FLASHBACK TABLE t1 TO BEFORE DROP — restores table, indexes, constraints.
• PURGE TABLE t1 — permanently removes from recycle bin.
• PURGE RECYCLEBIN — clears current user's recycle bin.
• PURGE DBA_RECYCLEBIN — DBA clears all users' bins.

VIEWS: USER_RECYCLEBIN, DBA_RECYCLEBIN.


WHEN TO DISABLE:
• Very high-throughput DDL environments where recycle bin accumulates thousands of objects, degrading data dictionary performance.
• Automated migration/ETL processes that drop/recreate tables frequently.
• DISABLE: ALTER SYSTEM SET RECYCLEBIN = OFF SCOPE=BOTH; or per-session: ALTER SESSION SET RECYCLEBIN = OFF;
• DROP TABLE t1 PURGE — bypasses recycle bin for a single operation.

CAUTION: Disabling recycle bin removes the last line of defense against accidental DROP — compensate with more frequent backups and Flashback Database.

TECHNICAL Oracle Database Vault
Q8: How does Oracle Database Vault work and when would you implement it?
▼ Show Model Answer

Oracle Database Vault (ODV) prevents privileged database users (including DBAs with DBA role) from accessing application data they should not see — implementing 'separation of duties.'


KEY CONCEPTS:
• Realms: Protected zones around schemas/objects. Even users with DBA or SELECT ANY TABLE cannot query realm-protected objects without being a realm participant.
• Command Rules: Control who can execute specific SQL commands (e.g., who can CREATE USER, ALTER SYSTEM).
• Factors: Contextual attributes used in access decisions (IP address, session user, time of day, application name).
• Rule Sets: Logical combinations of factors that evaluate to TRUE or FALSE.
• Secure Application Roles: Roles that can only be set by a trusted PL/SQL procedure using factors.

TYPICAL USE CASES:
• Financial/healthcare environments where DBAs should not read customer PII/PHI.
• PCI-DSS, HIPAA, SOX compliance requirements.
• Preventing insider threats from privileged accounts.
• Outsourced DBA arrangements.

IMPLEMENTATION CONSIDERATIONS:
• ODV requires careful design — a misconfigured realm can lock out legitimate access.
• Test thoroughly in non-production first.
• Always maintain a break-glass DV Owner account documented and secured.
• Monitor via DVSYS views and Unified Audit Trail.
TECHNICAL DBMS_SCHEDULER
Q9: Explain Oracle Scheduler — how would you create a complex job chain?
▼ Show Model Answer

Oracle Scheduler (DBMS_SCHEDULER) provides enterprise-grade job scheduling with dependencies, calendars, prioritization, and event-driven execution.


JOB CHAIN ARCHITECTURE:

1. Create Programs (the executable units):

DBMS_SCHEDULER.CREATE_PROGRAM('EXTRACT_DATA', 'STORED_PROCEDURE', 'pkg_etl.extract', 0, TRUE);


2. Create Schedule (time expression):

DBMS_SCHEDULER.CREATE_SCHEDULE('NIGHTLY_2AM', repeat_interval=>'FREQ=DAILY;BYHOUR=2;BYMINUTE=0');


3. Create Chain:

DBMS_SCHEDULER.CREATE_CHAIN('ETL_CHAIN');

DBMS_SCHEDULER.DEFINE_CHAIN_STEP('ETL_CHAIN','STEP1','EXTRACT_DATA');

DBMS_SCHEDULER.DEFINE_CHAIN_STEP('ETL_CHAIN','STEP2','TRANSFORM_DATA');

DBMS_SCHEDULER.DEFINE_CHAIN_STEP('ETL_CHAIN','STEP3','LOAD_DATA');


4. Define Rules (dependencies):

DBMS_SCHEDULER.DEFINE_CHAIN_RULE('ETL_CHAIN','TRUE','START STEP1');

DBMS_SCHEDULER.DEFINE_CHAIN_RULE('ETL_CHAIN','STEP1 SUCCEEDED','START STEP2');

DBMS_SCHEDULER.DEFINE_CHAIN_RULE('ETL_CHAIN','STEP2 SUCCEEDED','START STEP3');

DBMS_SCHEDULER.DEFINE_CHAIN_RULE('ETL_CHAIN','STEP1 FAILED','END -1'); -- fail chain


5. Create Job to run the chain:

DBMS_SCHEDULER.CREATE_JOB('ETL_NIGHTLY','CHAIN','ETL_CHAIN',schedule_name=>'NIGHTLY_2AM',enabled=>TRUE);


MONITORING: DBA_SCHEDULER_JOB_RUN_DETAILS, DBA_SCHEDULER_RUNNING_JOBS, DBA_SCHEDULER_JOB_LOG.

TECHNICAL Partitioning Strategies
Q10: What are the different partitioning strategies in Oracle and when do you use each?
▼ Show Model Answer

Partitioning divides large tables into smaller, manageable pieces while appearing as one object to SQL.


RANGE: Most common. Based on contiguous value ranges (dates, numeric IDs).

Use: Date-based data; time-series; monthly/quarterly archiving. Enables partition pruning.


LIST: Based on discrete values.

Use: Geographic regions, status codes, department IDs. Good for finite known values.


HASH: Even distribution across N partitions based on hash of partition key.

Use: When no natural range/list makes sense; to eliminate hot spots in OLTP; reduce contention.


COMPOSITE (subpartitioning): RANGE-HASH, RANGE-LIST, LIST-HASH.

Use: Date-partitioned data that also needs hash distribution within each date partition.


INTERVAL: Automatic RANGE — Oracle creates new partitions as data arrives.

Use: Time-series data where new months/days arrive continuously; eliminates manual partition maintenance.


REFERENCE: Partitions a child table using the partitioning of its parent (via FK).

Use: Keeps related parent/child data in same partition for collocated joins.


VIRTUAL COLUMN: Partition on a derived expression.

Use: When natural partition key doesn't exist but an expression of columns does.


KEY BENEFITS: Partition pruning (WHERE date BETWEEN ... eliminates irrelevant partitions), partition-wise joins, partition exchange (fast load/archive), parallel partition operations.


GOTCHA: Partition key must be NOT NULL for interval partitioning; global indexes become unusable during partition operations unless NOLOGGING or index rebuilding is planned.

TECHNICAL Oracle Net Configuration
Q11: How do you configure and tune Oracle Net (listener, tnsnames, connection pooling)?
▼ Show Model Answer

Oracle Net handles all client-to-database and database-to-database network communication.


LISTENER (listener.ora):
• Static vs. Dynamic registration: Prefer dynamic (PMON registers DB automatically).
• VALID_NODE_CHECKING: Restrict connections by IP (security best practice).
• INBOUND_CONNECT_TIMEOUT: Prevent half-open connection attacks.
• SUBSCRIBE_FOR_NODE_DOWN_EVENT: Enable FAN events for fast connection failover.
• RELOAD: lsnrctl reload (no downtime); full restart only when changing ports.

TNSNAMES.ORA / LDAP: For small environments, tnsnames.ora; for large: Oracle Internet Directory (LDAP/OID) or Easy Connect Plus (19c+).


EASY CONNECT PLUS (19c+): hostname:port/service?wallet_location=/wallets — no tnsnames needed for simple connections.


CONNECTION POOLING OPTIONS:
• DRCP (Database Resident Connection Pooling): Broker shares server processes among clients. Ideal for web tier with thousands of short-lived connections. Enable: DBMS_CONNECTION_POOL.START_POOL; use SERVICE=mydb:POOLED in connect string.
• CMAN (Connection Manager): Multiplexes connections, provides firewall-like filtering. Use for DMZ architectures.

SQLNET.ORA KEY PARAMETERS:
• SQLNET.EXPIRE_TIME: Dead connection detection (minutes). Set to 10 for cloud environments.
• SQLNET.ENCRYPTION_CLIENT/SERVER: Native Network Encryption.
• SQLNET.INBOUND_CONNECT_TIMEOUT: Prevent SYN flood attacks on listener.

TUNING: SDU (Session Data Unit) — default 8KB; increase to 32KB–64KB for bulk data transfer. RECV_BUF_SIZE, SEND_BUF_SIZE for throughput tuning.

TECHNICAL Unified Auditing
Q12: Explain Oracle Unified Auditing — how is it configured and what are its advantages over traditional auditing?
▼ Show Model Answer

Unified Auditing (introduced in 12c) consolidates all audit records from database audit, FGA (Fine-Grained Auditing), RMAN, DataPump, Label Security, Database Vault, and Real Application Security into a single AUDSYS schema in the SYSAUX tablespace.


ENABLING: In 12c+, mixed mode is default (traditional + unified). Full unified mode requires relink:

cd $ORACLE_HOME/rdbms/lib && make -f ins_rdbms.mk uniaud_on ioracle


AUDIT POLICIES:

CREATE AUDIT POLICY dba_actions_policy

PRIVILEGES CREATE ANY TABLE, DROP ANY TABLE

ACTIONS UPDATE ON hr.employees, DELETE ON hr.employees

WHEN 'SYS_CONTEXT(''USERENV'',''SESSION_USER'') != ''APPUSER'''

EVALUATE PER SESSION;

AUDIT POLICY dba_actions_policy;


ADVANTAGES OVER TRADITIONAL:
• Single unified view: UNIFIED_AUDIT_TRAIL (replaces AUD$, FGA_LOG$, SYS.AUD$).
• Conditional policies (WHEN clause) — audit only specific contexts.
• PER SESSION vs. PER ACCESS granularity.
• No performance hit from writing to AUD$ during transaction — audit written after commit.
• Tamper-resistant (written by AUDSYS, not accessible by DBA without specific privilege).
• Covers RMAN operations, Data Pump, OS audit records in one place.

ARCHIVING: Use DBMS_AUDIT_MGMT to set retention and flush policies. Archive to external SIEM.

TECHNICAL Result Cache
Q13: What is Oracle Result Cache and when would you use or avoid it?
▼ Show Model Answer

The Result Cache stores the results of SQL queries and PL/SQL functions in the shared pool so subsequent identical executions return cached results without re-executing.


SQL RESULT CACHE: Results cached in SGA based on exact SQL text + bind values.

/*+ RESULT_CACHE */ hint or RESULT_CACHE MODE FORCE at table level. SELECT /*+ RESULT_CACHE */ count(*) FROM dim_product WHERE active='Y';

PL/SQL FUNCTION RESULT CACHE: Cache function return values keyed by input parameters.

CREATE OR REPLACE FUNCTION get_rate(p_curr IN VARCHAR2) RETURN NUMBER

RESULT_CACHE RELIES_ON (exchange_rates) IS ...

— Oracle automatically invalidates cache when exchange_rates table changes.


VIEWS: V$RESULT_CACHE_STATISTICS, V$RESULT_CACHE_OBJECTS, V$RESULT_CACHE_MEMORY.


GOOD USE CASES:
• Reference data that changes infrequently (currency rates, lookup tables, configuration).
• Expensive aggregate queries called repeatedly.
• Reporting queries on slowly changing dimensional data.

WHEN TO AVOID:
• Highly volatile tables (cache invalidated too frequently = overhead without benefit).
• Large result sets (cache memory is finite, from shared pool).
• Queries with non-deterministic functions (SYSDATE, DBMS_RANDOM).
• High-concurrency OLTP where same query is rarely repeated with same parameters.

SIZING: RESULT_CACHE_MAX_SIZE (default: 0.25% of SGA or 75% of shared pool — whichever smaller). Monitor hit ratio in V$RESULT_CACHE_STATISTICS.

TECHNICAL In-Memory Column Store
Q14: How do you manage and monitor Oracle's In-Memory Column Store (IMCS)?
▼ Show Model Answer

Oracle's In-Memory Column Store (IMCS, introduced 12.1.0.2) stores table data in a columnar format in a dedicated SGA area (IM column store) for dramatically faster analytics, without changing SQL.


ENABLING:
ALTER SYSTEM SET INMEMORY_SIZE = 20G SCOPE=SPFILE; -- restart required ALTER TABLE sales INMEMORY PRIORITY CRITICAL; -- populate on next access ALTER TABLE sales INMEMORY MEMCOMPRESS FOR QUERY LOW; -- compression level

POPULATION PRIORITIES: NONE (on first access), LOW, MEDIUM, HIGH, CRITICAL (on DB open).

POPULATE status: SELECT segment_name, bytes, bytes_not_populated, inmemory_priority

FROM v$im_segments;


COMPRESSION LEVELS: FOR DML (min), FOR QUERY LOW, FOR QUERY HIGH, FOR CAPACITY LOW, FOR CAPACITY HIGH (max).


HOW IT HELPS:
• Eliminates row-by-row scan for analytics — columnar format scans only relevant columns.
• SIMD (Single Instruction Multiple Data) vector processing on compressed columns.
• Join Groups: Pre-computes hash joins between common join columns across tables.
• Bloom Filters: Reduces data shipped in parallel join operations.

MONITORING: V$IM_SEGMENTS, V$INMEMORY_AREA, V$IM_COLUMN_LEVEL, GV$IM_SEGMENTS (RAC).


WHEN NOT TO USE: Pure OLTP with single-row lookups — IMCS provides no benefit and wastes memory. Target large analytical tables scanned frequently.

TECHNICAL Global Temporary Tables
Q15: Explain Global Temporary Tables (GTTs) and their use cases vs. regular tables.
▼ Show Model Answer

GTTs are permanent table definitions that hold data temporarily — data exists only for the duration of a transaction (ON COMMIT DELETE ROWS) or session (ON COMMIT PRESERVE ROWS).


CREATE GLOBAL TEMPORARY TABLE session_cart (

item_id NUMBER, quantity NUMBER, price NUMBER

) ON COMMIT PRESERVE ROWS; -- data lives for the session


CREATE GLOBAL TEMPORARY TABLE stage_data (

id NUMBER, value VARCHAR2(100)

) ON COMMIT DELETE ROWS; -- data cleared after each COMMIT


KEY CHARACTERISTICS:
• Each session sees only its own data — completely session-isolated.
• No undo generated for DML (only redo for undo blocks — much less logging than permanent tables).
• Statistics: gathered per-session in 12c+ (dynamic statistics or DBMS_STATS with dynamic_sampling).
• No direct-path insert (INSERT /*+ APPEND */) support.
• Cannot have FK references from/to permanent tables.
• In 18c+: Private Temporary Tables (PTT) — defined and visible only within a single session, dropped automatically. No DDL needed across sessions.

USE CASES:
• Complex multi-step ETL within a session — avoid re-querying intermediate results.
• Storing session-specific working sets (shopping carts, report parameters).
• Breaking up complex SQL into manageable steps with temporary storage.
• Avoiding lock contention on shared staging tables.

PERFORMANCE NOTE: GTTs generate no undo but still generate redo (for undo blocks). For truly minimal logging, consider collections (PL/SQL arrays) for small datasets.

Oracle DataGuard

High Availability, Disaster Recovery & Standby Operations
11 Questions
DataGuard questions are among the most common in senior Oracle DBA interviews. Expect architecture questions, configuration specifics, failover procedures, and real-world troubleshooting scenarios.
TECHNICAL Protection Modes
Q1: Compare the three DataGuard protection modes — Maximum Protection, Maximum Availability, and Maximum Performance.
▼ Show Model Answer

MAXIMUM PROTECTION (zero data loss, no fallback):

• Redo sent to standby synchronously (SYNC) + AFFIRM (standby writes to disk before ACK).
• Primary shuts down if it cannot write to at least one standby. Zero data loss guaranteed.
• Use: Financial trading, banking core systems where RPO = 0 is non-negotiable.
• Risk: Primary outage if standby is unavailable (no fallback to async).

MAXIMUM AVAILABILITY (zero data loss, with fallback):

• Same as Protection: SYNC + AFFIRM. But if all standbys become unavailable, primary automatically falls back to Maximum Performance (async) mode and continues.
• Primary does NOT shut down on standby loss — key operational difference.
• Use: Most mission-critical production systems. Best balance of protection and availability.
• Recovery after re-connection: automatically re-syncs gap and returns to sync mode.

MAXIMUM PERFORMANCE (best performance, possible data loss):

• Redo sent asynchronously (ASYNC). Primary does not wait for standby acknowledgement.
• Best primary database performance; possible data loss (seconds to minutes) if primary fails.
• Use: Development/test standbys, read offload standbys, geographically distant DR sites where sync latency is prohibitive.

CHANGE MODE: ALTER DATABASE SET STANDBY DATABASE TO MAXIMIZE AVAILABILITY;

VERIFY: SELECT protection_mode, protection_level FROM V$DATABASE;

NOTE: Protection_level may differ from protection_mode if fallback has occurred.

TECHNICAL Redo Transport
Q2: Explain the DataGuard redo transport services — all relevant parameters and process interactions.
▼ Show Model Answer

Redo transport moves redo from the primary to standby databases via Oracle Net.


PRIMARY SIDE PROCESSES:
• LGWR or ARCH sends redo (LGWR for synchronous/low-latency; ARCH for async from archived logs).
• LNS (Log Network Server): Network I/O process for sending redo. One LNS per standby.
• In 12c+: Integrated redo transport uses LGWR-based shipping by default.

STANDBY SIDE PROCESSES:
• RFS (Remote File Server): Receives redo from primary, writes to standby redo logs.
• MRP (Managed Recovery Process): Applies redo from standby redo logs to standby datafiles (MANAGED RECOVERY).

KEY LOG_ARCHIVE_DEST_n PARAMETERS:

LOG_ARCHIVE_DEST_2 = 'SERVICE=standby_tns SYNC AFFIRM VALID_FOR=(ONLINE_LOGFILES,PRIMARY_ROLE) DB_UNIQUE_NAME=STBY'

• SERVICE: TNS name of standby

• SYNC/ASYNC: Synchronous or asynchronous transport

• AFFIRM/NOAFFIRM: Whether standby must write to disk before ACKing

• COMPRESSION=ENABLE: Compress redo before sending (CPU for bandwidth tradeoff)

• ENCRYPTION=ENABLE: Encrypt redo in transit (requires Oracle Advanced Security)

• MAX_FAILURE=n: Attempts before failing over to next dest

• REOPEN=n: Seconds before retrying after failure


MONITORING TRANSPORT:

V$ARCHIVE_DEST_STATUS — current status of each destination

V$DATAGUARD_STATS — apply lag, transport lag

V$MANAGED_STANDBY — LNS/RFS/MRP process status

TECHNICAL Switchover Procedure
Q3: Walk me through a complete planned switchover procedure for a DataGuard configuration.
▼ Show Model Answer

A switchover is a planned, reversible role transition with no data loss. Both databases must be in sync.


PRE-CHECKS:

1. Verify primary: SELECT switchover_status FROM v$database; → should be 'TO STANDBY' or 'SESSIONS ACTIVE'

2. Verify standby is current: SELECT name, value FROM v$dataguard_stats WHERE name = 'apply lag';

3. Check no uncommitted distributed transactions: SELECT * FROM dba_2pc_pending;

4. Notify application teams; plan maintenance window.


STEP 1 — Switch Primary to Standby Role:

ALTER DATABASE COMMIT TO SWITCHOVER TO PHYSICAL STANDBY WITH SESSION SHUTDOWN;

(On primary — converts primary to a standby mount state)


STEP 2 — Shutdown and Restart the (now-standby) database:

SHUTDOWN IMMEDIATE; STARTUP MOUNT;


STEP 3 — Activate the Standby as New Primary:

On standby: SELECT switchover_status FROM v$database; → should show 'TO PRIMARY'

ALTER DATABASE COMMIT TO SWITCHOVER TO PRIMARY WITH SESSION SHUTDOWN; ALTER DATABASE OPEN;

STEP 4 — Start Managed Recovery on the new standby (old primary):

ALTER DATABASE RECOVER MANAGED STANDBY DATABASE USING CURRENT LOGFILE DISCONNECT;
POST-SWITCHOVER:
• Update application connection strings (SCAN, service names).
• Verify DataGuard Broker status: SHOW CONFIGURATION (in DGMGRL).
• Confirm redo transport resumed: V$ARCHIVE_DEST_STATUS.
• Update monitoring tools.

WITH BROKER (simpler): DGMGRL> SWITCHOVER TO standby_name — handles all steps automatically.

TECHNICAL Active DataGuard
Q4: What is Active DataGuard and what operations does it enable? What are the licensing implications?
▼ Show Model Answer

Active DataGuard (ADG) allows the physical standby database to be OPEN READ ONLY while MRP (Managed Recovery Process) continues applying redo in real-time. Standard DataGuard requires the standby to be in MOUNT state (not open) while applying.


CAPABILITIES ENABLED BY ACTIVE DATAGUARD:
• Read-only query offload from primary — reporting, analytics, extracts.
• Real Application Testing (replay workload on standby).
• Automatic block repair: If primary detects a corrupt block, it automatically fetches the good block from standby (and vice versa). Requires ADG.

TECHNICAL Gap Resolution
Q6: How do you resolve an archive gap on a DataGuard standby?
▼ Show Model Answer

An archive gap occurs when the standby is missing one or more archived redo logs that the primary has already generated and potentially overwritten. The standby cannot apply redo until the gap is resolved.


DETECT GAP:

On standby: SELECT * FROM v$archive_gap; -- shows first/last missing sequence

On primary: SELECT thread#, sequence# FROM v$archived_log WHERE applied='NO' ORDER BY sequence#;

DGMGRL: SHOW DATABASE VERBOSE standby_db; -- shows apply lag and gap info


AUTOMATIC RESOLUTION (preferred): DataGuard automatically detects gaps and fetches missing logs from the primary via FAL (Fetch Archive Log) mechanism.

FAL_SERVER = primary_db (set on standby)

FAL_CLIENT = standby_db (set on standby)

This happens automatically — just ensure the standby can reach the primary.


MANUAL RESOLUTION (when auto-fetch fails):

1. Identify missing sequences from v$archive_gap.

2. Copy missing archive logs from primary (or another standby) to standby arc destination.

3. Register the logs: ALTER DATABASE REGISTER PHYSICAL LOGFILE '/arch/1_45_123456.arc';

4. MRP will pick up and apply.


RMAN BACKUP-BASED RESOLUTION (large gap — easier than manual copy):

On standby: RMAN> RECOVER DATABASE; -- RMAN fetches from primary automatically via net.

Or: RMAN> RECOVER STANDBY DATABASE; (12c+ command specifically for standby gap recovery)


PREVENTION: Ensure archive log retention policy on primary keeps logs long enough for standby to catch up after any outage. Monitor V$ARCHIVE_DEST_STATUS for DEFERRED or ERROR status daily.

TECHNICAL Snapshot Standby
Q7: What is a Snapshot Standby and when would you use it?
▼ Show Model Answer

A Snapshot Standby converts a physical standby into a fully writable database, while preserving the ability to return it to a physical standby with all redo applied since the conversion.


HOW IT WORKS:
• Conversion creates a Guaranteed Restore Point on the standby.
• MRP is stopped; standby is opened in READ WRITE mode.
• All changes made while in snapshot mode are tracked (using Flashback Database).
• On reversion: Flashback database to the restore point → discard all snapshot changes → restart MRP → standby catches up with primary redo.

CONVERT TO SNAPSHOT: DGMGRL> CONVERT DATABASE standby_db TO SNAPSHOT STANDBY;

Or manually: ALTER DATABASE CONVERT TO SNAPSHOT STANDBY;


REVERT TO PHYSICAL: DGMGRL> CONVERT DATABASE standby_db TO PHYSICAL STANDBY;

(Discards all snapshot-mode changes, resumes redo apply)


USE CASES:
• Application testing against production data without impacting the primary.
• Developer or QA access to real data for testing (with data masking where required).
• Database upgrade testing on a copy of production data.
• Patch testing — apply patch to snapshot standby, test, then revert.

REQUIREMENTS:
• Flashback Database must be enabled on the standby (DB_RECOVERY_FILE_DEST must be configured).
• Sufficient FRA space to hold flashback logs for the snapshot period.
• Protection level must not be Maximum Protection (primary not dependent on this standby during snapshot).

CAVEAT: While in snapshot mode, the standby does NOT protect the primary — redo is still being transported but not applied. Plan snapshot windows carefully.

TECHNICAL Rolling Upgrade with DG
Q8: How does DataGuard handle the redo apply during a rolling upgrade (transient logical standby)?
▼ Show Model Answer

Oracle's Active DataGuard Rolling Upgrade process uses a Transient Logical Standby (TLS) to upgrade the standby first while the primary remains on the old version — maintaining database availability throughout.


ROLLING UPGRADE PROCESS (Oracle 11g+):

1. Convert physical standby to logical standby (temporarily):

Primary: ALTER DATABASE COMMIT TO SWITCHOVER TO LOGICAL STANDBY;

Standby: ALTER DATABASE RECOVER TO LOGICAL STANDBY db_name;


2. Upgrade the logical standby (now writable) to new Oracle version.

Run DBUA or AutoUpgrade on the logical standby.


3. Start SQL Apply on the upgraded logical standby — it continues receiving and applying redo from the (older) primary.


4. Switchover: old primary (lower version) becomes a logical standby; upgraded database becomes primary.


5. Upgrade the old primary (now standby) to the new version.


6. Convert back to physical standby: reconcile with new primary using RMAN.


ORACLE 12.2+ DBMS_ROLLING PACKAGE: Automates this entire process including the transient logical standby conversion and switchover.

DBMS_ROLLING.BEGIN_UPGRADE; DBMS_ROLLING.SWITCHOVER; DBMS_ROLLING.FINISH_UPGRADE;


KEY BENEFIT: Zero planned downtime for Oracle version upgrades — users stay connected to the primary throughout.

REQUIREMENTS: Active DataGuard license for the rolling upgrade period; Enterprise Edition.

TECHNICAL Far Sync Instance
Q10: What is a Far Sync Instance and when would you use it?
▼ Show Model Answer

A Far Sync instance is a lightweight Oracle instance that has no datafiles — only a control file, spfile, and standby redo logs. It acts as a redo transport intermediary between the primary and a distant standby.


THE PROBLEM IT SOLVES:
• You want zero data loss (sync transport) but your DR standby is geographically far away.
• SYNC transport over long distances introduces unacceptable latency to primary commits (round-trip to Sydney from New York adds ~160ms per commit).

FAR SYNC SOLUTION:

Primary → SYNC → Far Sync (nearby, e.g., same datacenter or metro distance) → ASYNC → Distant Standby


• Primary commits synchronously to Far Sync (minimal latency — nearby).
• Far Sync forwards redo asynchronously to the distant standby (no latency impact on primary).
• Result: zero data loss guaranteed between primary and Far Sync; async propagation beyond.

SETUP (requires Active DataGuard license):
• Far Sync instance: CREATE CONTROLFILE as standby; no datafiles; configure as intermediate dest.
• Primary LOG_ARCHIVE_DEST_2: SERVICE=far_sync SYNC AFFIRM
• Far Sync LOG_ARCHIVE_DEST_2: SERVICE=distant_standby ASYNC NOAFFIRM

BENEFITS:
• Zero data loss with minimal performance impact.
• Far Sync can serve multiple distant standbys simultaneously.
• Cascaded redo forwarding — Far Sync fans out to multiple standbys.
• No licensing for Far Sync instance itself (but requires ADG license on primary).
SCENARIO Troubleshooting
SCENARIO: Your DataGuard standby shows 'MRP0 — WAIT_FOR_LOG' and the apply lag is growing. Transport lag shows 0. What do you investigate?
▼ Show Model Answer

Transport lag = 0 means logs ARE reaching the standby. MRP is WAITING for logs but not applying — this is a gap in sequence numbers.


INVESTIGATION STEPS:

1. Check what sequence MRP is waiting for:

SELECT process, status, sequence# FROM v$managed_standby WHERE process LIKE 'MRP%';

2. Check what's available in the standby redo logs:

SELECT sequence#, first_change#, next_change# FROM v$standby_log WHERE used='YES';

3. Check if the standby redo log is not being archived on the standby:

SELECT sequence#, applied FROM v$archived_log WHERE thread#=1 ORDER BY sequence# DESC;

4. Check if STANDBY_FILE_MANAGEMENT=AUTO (required for standby redo logs to auto-create).


5. MOST LIKELY CAUSES:

a) Standby redo log (SRL) not added — RFS cannot write current redo. Add SRLs matching primary log size + one extra.

b) SRL full but archiver on standby not running (ARC process stopped).

c) Primary just added a redo log group — standby doesn't have matching SRL.

d) FRA full on standby — cannot archive the SRL.


FIX: Ensure standby has SRL groups = primary online log groups + 1, same size.

ALTER DATABASE ADD STANDBY LOGFILE GROUP 5 '/stdby/srl05.log' SIZE 1G;

Monitor: SELECT group#, bytes, used, status FROM v$standby_log;

TECHNICAL Normalization Forms
Q1: Explain the normalization forms (1NF through BCNF) with examples. When would you deliberately denormalize?
▼ Show Model Answer

NORMALIZATION reduces data redundancy and improves data integrity through decomposition.


1NF (First Normal Form):

• Eliminate repeating groups; each cell contains atomic (indivisible) values; primary key exists.
• Violation: ORDER table with ITEM1, ITEM2, ITEM3 columns → fix: separate ORDER_ITEMS table.

2NF (Second Normal Form):

• 1NF + every non-key attribute fully dependent on the ENTIRE primary key (no partial dependency).
• Only applies when PK is composite.
• Violation: ORDER_ITEMS(order_id, product_id, product_name) — product_name depends only on product_id.
• Fix: Move product_name to PRODUCTS table.

3NF (Third Normal Form):

• 2NF + no transitive dependencies (non-key attributes cannot depend on other non-key attributes).
• Violation: EMPLOYEE(emp_id, dept_id, dept_name) — dept_name depends on dept_id, not emp_id.
• Fix: Separate DEPARTMENT table.

BCNF (Boyce-Codd Normal Form):
• Stricter 3NF: every determinant must be a candidate key.
• Handles anomalies that 3NF misses in tables with multiple overlapping candidate keys.

DELIBERATE DENORMALIZATION — when justified:
• Reporting/Analytics: Pre-join tables to avoid expensive runtime joins (star schema, flattened reporting tables).
• High-read OLTP with read:write > 100:1: storing derived/aggregate values.
• Archive tables: Flatten for independent queryability without lookups.
• When profiling proves JOIN cost exceeds storage/update cost of redundancy.

Rule: Always normalize first, denormalize with benchmarks as proof.

TECHNICAL Star vs Snowflake
Q2: Compare Star Schema vs. Snowflake Schema for a data warehouse. What are the tradeoffs?
▼ Show Model Answer

STAR SCHEMA: Fact table at center, surrounded by fully denormalized dimension tables.

• Structure: FACT_SALES → DIM_CUSTOMER, DIM_PRODUCT, DIM_TIME, DIM_STORE
• DIM_CUSTOMER contains all customer attributes in one wide table (no sub-dimensions).
• ADVANTAGE: Simple joins (single JOIN per dimension), fast queries, easy for BI tools to understand.
• DISADVANTAGE: Data redundancy in dimensions (same city/state repeated for every customer), update anomalies.
• BEST FOR: OLAP, business intelligence, ad-hoc reporting, Tableau/Power BI consumption.

SNOWFLAKE SCHEMA: Fact table with normalized dimension tables (sub-dimensions).

• DIM_PRODUCT → DIM_CATEGORY → DIM_DEPARTMENT (each normalized level is a separate table).
• ADVANTAGE: Eliminates dimension data redundancy; easier to maintain dimension hierarchies; smaller storage.
• DISADVANTAGE: More complex joins; query performance typically lower without good indexing/partitioning; harder for BI tools.
• BEST FOR: Very large dimensions with significant hierarchy depth; environments where dimension update frequency is high.

ORACLE-SPECIFIC CONSIDERATIONS:
• Star schema benefits from bitmap indexes on dimension FK columns in the fact table.
• Oracle optimizer's star transformation: rewrites query to use bitmap ANDs on FK columns for massive speedup.
• Enable: STAR_TRANSFORMATION_ENABLED=TRUE (optimizer parameter).
• In-Memory Column Store (IMCS) with Join Groups eliminates much of the star vs. snowflake performance difference.

REAL WORLD: Most production DWs use a HYBRID — some snowflaking for shared large dimensions (geography), star for query-critical dimensions.

TECHNICAL SCD Types
Q3: What are Slowly Changing Dimensions (SCDs) and how do you implement Types 1, 2, and 3?
▼ Show Model Answer

SCDs handle how dimension attributes change over time in a data warehouse.


SCD TYPE 1 — Overwrite (No History):

• Simply update the dimension record with the new value. No history preserved.
• Use: Corrections, minor attribute changes where history is irrelevant (spelling correction, phone number format).
• Implementation: Simple UPDATE on the dimension row.
• Impact on Oracle: Update all affected bitmap indexes; consider deferred index maintenance.

SCD TYPE 2 — Add New Row (Full History):

• Insert a new dimension row with new values; mark old row as expired.
• Add columns: EFFECTIVE_DATE, EXPIRY_DATE, IS_CURRENT flag, surrogate key.
• Example: Customer moves from NY to CA → new DIM_CUSTOMER row for CA; old row expired.
• Historical fact rows retain FK to old dimension row (preserving historical context).
• Implementation in Oracle: Conditional INSERT via MERGE; maintain surrogate keys using sequences.
• CHALLENGE: Dimension table grows continuously; partition by IS_CURRENT for query performance.

SCD TYPE 3 — Add New Column (Limited History):

• Add a 'previous value' column alongside the current value. Only one level of history.
• Example: CURRENT_REGION='West', PRIOR_REGION='East'.
• Use: When only 'before/after last change' is needed; simpler than Type 2.
• Limitation: Cannot track more than one change back.

SCD TYPE 4 — Mini-Dimension:
• Rapidly changing attributes split into a separate mini-dimension table with own surrogate key.
• Use: Demographics (age band, income bracket) that change frequently — avoid bloating main dimension.

ORACLE IMPLEMENTATION TOOLS: MERGE statement, Oracle Warehouse Builder (OWB, legacy), ODI (Oracle Data Integrator), partitioning with enable_row_movement for Type 2.

TECHNICAL OLTP Schema Design
Q4: How do you design a database schema for high concurrency OLTP? Key considerations?
▼ Show Model Answer
HIGH CONCURRENCY OLTP DESIGN PRINCIPLES:

1. NARROW PRIMARY KEYS: Use surrogate number keys (from sequences or identity columns). Avoid wide natural keys — reduces index size, join overhead, undo size.


2. MINIMIZE LOCK CONTENTION:

• Avoid hot blocks: If many sessions INSERT sequentially, use REVERSE KEY indexes to distribute inserts across index blocks.

• For sequence-generated PKs: Use CACHE (1000+) sequences and NOCYCLE to minimize sequence latch contention. Consider NOORDER for RAC.

• Avoid frequent updates to indexed columns — causes index block splits.


3. RIGHT-SIZE BLOCKS AND PCTFREE:

• OLTP: PCTFREE=20–30 (leave space for updates to grow rows in-place, avoiding row migration).

• OLTP: Block size 8KB standard; avoid mixing block sizes unless justified.


4. PARTITION CAREFULLY:

• OLTP partitioning: Hash partition on PK/FK to distribute load.

• Avoid range partitioning on insert timestamp in OLTP — all inserts hit the same partition (hot spot).


5. INDEX DESIGN:

• Index foreign keys to prevent table-level lock escalation (missing FK index causes TM lock on parent during child insert/delete).

• B-tree indexes for OLTP (high selectivity, exact lookups).

• Avoid over-indexing — every index slows DML.

• Function-based indexes for frequent UPPER()/LOWER() searches.


6. SEQUENCE DESIGN FOR RAC: ORDER on sequences forces inter-node coordination. Use NOORDER unless application requires ordered IDs.


7. ROW CHAINING/MIGRATION: ANALYZE TABLE ... VALIDATE STRUCTURE; check for chained rows. Rebuild with ALTER TABLE ... MOVE when chaining > 5%.


8. DEFERRED CONSTRAINT CHECKING: For complex batch loads, use DEFERRABLE INITIALLY DEFERRED constraints to validate only at COMMIT time.

TECHNICAL Materialized Views
Q5: Explain materialized views — refresh types, when to use them, and how query rewrite works.
▼ Show Model Answer

A Materialized View (MV) is a database object that contains the results of a query — a precomputed, stored snapshot of a complex query result.


REFRESH TYPES:
• COMPLETE: Truncates and re-populates entire MV. Expensive but always accurate.

ON DEMAND: DBMS_MVIEW.REFRESH('mv_name','C');

ON COMMIT: Refreshes after every commit to base tables — only for simple MVs.


• FAST (Incremental): Uses MV logs (materialized view logs) to refresh only changed rows.

Requires: CREATE MATERIALIZED VIEW LOG ON base_table WITH ROWID, SEQUENCE, PRIMARY KEY INCLUDING NEW VALUES;

Restrictions: Cannot use FAST refresh with DISTINCT, GROUP BY with non-aggregate columns, certain analytic functions, or complex joins without careful design.


• FORCE: Oracle uses FAST if possible; falls back to COMPLETE.

• PARTITION CHANGE TRACKING (PCT): Fast refresh at the partition level — only refresh partitions with changes.

QUERY REWRITE: Oracle's optimizer transparently rewrites SQL against base tables to use the MV instead — without the user knowing.

ENABLE: ENABLE QUERY REWRITE on the MV; QUERY_REWRITE_ENABLED=TRUE (system param).

Test: EXPLAIN PLAN; look for MV name in plan instead of base tables.

Full QUERY REWRITE requires TRUSTED or ENFORCED integrity (so optimizer knows FK relationships).


USE CASES:
• Data warehouse pre-aggregations (daily/monthly summaries).
• Complex joins repeated by many queries (join MV).
• Replacing a complex view with poor performance.
• Eliminating redundant computation in ETL pipelines.

MONITORING: DBA_MVIEWS (refresh type, staleness), DBA_MVIEW_REFRESH_TIMES, DBA_MVIEW_LOGS.

TECHNICAL Data Vault
Q6: What is Data Vault modeling and how does it differ from Kimball and Inmon approaches?
▼ Show Model Answer

Data Vault is a modeling methodology designed for enterprise data warehouses that prioritizes agility, auditability, and historical tracking.


CORE COMPONENTS:
• Hubs: Business keys + metadata (load date, record source). Represent core business entities. No descriptive attributes. E.g., HUB_CUSTOMER (customer_hash_key, customer_id, load_date, record_source).
• Links: Relationships between Hubs (many-to-many by design). E.g., LINK_ORDER_CUSTOMER (link_key, customer_hash_key, order_hash_key, load_date).
• Satellites: Context and descriptive attributes for Hubs or Links, with full history. E.g., SAT_CUSTOMER_DETAILS (customer_hash_key, load_date, expiry_date, name, address, ...).

DESIGN PHILOSOPHY:
• All changes are INSERT-ONLY — no updates, no deletes. Complete audit trail by design.
• Hash keys (SHA-1/SHA-256 of business keys) enable parallel loads and source-agnostic joins.
• Extremely flexible for adding new sources or entities without restructuring existing tables.

VS. KIMBALL (Dimensional Modeling):
• Kimball: Optimized for query performance (star/snowflake schema, presentation layer).
• Data Vault: Optimized for agility and history (raw vault) + business rules applied in presentation layer.
• Modern DW uses BOTH: Data Vault as raw/integration layer → Business Vault → Kimball star schema as presentation/consumption layer.

VS. INMON (3NF Enterprise DW):
• Inmon: Highly normalized 3NF enterprise warehouse, then data marts.
• Data Vault: Like Inmon in that it's normalized, but adds explicit historization and source tracking.
• Data Vault is generally more scalable for multi-source integration than Inmon 3NF.

ORACLE IMPLEMENTATION: Parallel INSERT with hash key generation using STANDARD_HASH(); partition Satellites by load_date for performance.

TECHNICAL Index Design Strategy
Q7: How do you approach index design for a new schema? What types and when?
▼ Show Model Answer

INDEX DESIGN FRAMEWORK — Always start with the workload, not the schema.


STEP 1: Identify access patterns from application SQL, AWR top SQL, or SQL advisor.

STEP 2: Design for the most frequent/expensive queries first.


INDEX TYPES AND WHEN TO USE:

B-TREE (Default): Use for high-cardinality columns with exact match or range predicates.

• UNIQUE B-Tree: Enforce uniqueness + fastest lookup. Use for PKs and unique constraints.
• Composite B-Tree: Column order matters — put most selective column first UNLESS range predicate is on second column (then reverse). WHERE order matters for index skip scans.
• REVERSE KEY: Distributes sequential inserts across leaf blocks. Use for sequence-generated PKs in RAC or high-insert scenarios to eliminate right-hand index block contention.

BITMAP INDEX: Use for low-cardinality columns in read-heavy DW environments (status, region, gender).

• DO NOT use in OLTP — row-level bitmap lock escalates to block level, causing massive contention.
• EXTREMELY efficient for multi-column AND/OR queries in DW (bitmap operations before row access).

FUNCTION-BASED INDEX (FBI): Index on an expression/function result.

• Use when queries use UPPER(name), TRUNC(date), or custom expressions in WHERE clause.
• CREATE INDEX idx_upper_name ON customers (UPPER(last_name));

PARTIAL INDEX (12c+): Index with a WHERE clause — only indexes rows matching the condition.

• CREATE INDEX idx_active ON orders (order_date) WHERE status='ACTIVE';
• Massively smaller index for queries that always filter on that condition.

INVISIBLE INDEX (11g+): Index exists but optimizer ignores it. Use for testing index impact without affecting production queries.

• ALTER INDEX idx_test INVISIBLE; → test; → ALTER INDEX idx_test VISIBLE;

INDEX COMPRESSION: Prefix compression for composite indexes with repeated leading columns. Can halve index size.


MONITORING: V$OBJECT_USAGE (track index usage); SYS.COL_USAGE$ (which columns are predicated upon).

TECHNICAL HTAP Design
Q8: What are the considerations for designing a schema for both OLTP and analytical queries (HTAP)?
▼ Show Model Answer

Hybrid Transactional and Analytical Processing (HTAP) refers to systems that must serve both OLTP and OLAP workloads on the same data.


ORACLE'S HTAP TOOLS:
• In-Memory Column Store: Store critical tables in columnar format (IMCS) for analytics while maintaining row-store for OLTP. Both occur simultaneously without schema changes.
• Active DataGuard: Route all analytical/reporting queries to the read-only ADG standby — primary serves OLTP only.
• Partitioning: Partition by time; recent partitions optimized for OLTP (row access), older partitions with bitmap indexes for analytics.

SCHEMA DESIGN CONSIDERATIONS:

1. Avoid wide rows with many nullable columns — hurts columnar efficiency.

2. Choose appropriate data types (NUMBER(p,s) not VARCHAR2 for numeric data).

3. Use partitioning to separate hot (OLTP) from cold (analytics) data.

4. Foreign keys with proper indexes serve both: FK enforcement for integrity (OLTP) + join enablement (OLAP).

5. Maintain statistics aggressively — both row-store and IMCS depend on accurate stats.

6. Consider separate schemas for OLTP (normalized) and materialized reporting schema (denormalized) — sync via triggers or DBMS_MVIEW.


RESOURCE MANAGEMENT:
• Use Oracle Resource Manager to allocate CPU/memory between OLTP and analytics consumer groups.
• Priority: OLTP sessions get higher priority; analytics sessions throttled during peak OLTP hours.
• PGA_AGGREGATE_TARGET: Ensure large analytical sorts don't starve OLTP sessions.
TECHNICAL Referential Integrity
Q9: How do you handle referential integrity in a high-volume OLTP system? When would you drop FK constraints?
▼ Show Model Answer

Referential integrity (RI) via foreign keys is critical for data quality but has real performance implications in high-volume systems.


FK CONSTRAINT PERFORMANCE IMPACTS:

1. MISSING INDEX ON FK COLUMN: Without an index on the child table's FK column:

• DELETE from parent table causes a FULL TABLE SCAN of the child table to check for child rows.

• More critically: A TM (table-level) lock (mode 4 = Share) is placed on the child table during parent DELETE/UPDATE — blocking all concurrent DML on the child table.

• ALWAYS index FK columns. Rule: Every FK in the child table must have a leading index.


2. INSERT on child: Oracle verifies parent exists → consistent read of parent (lightweight, index access).


3. DELETE on parent with ON DELETE CASCADE: Cascades through all child levels — can be very expensive.


WHEN TO DISABLE/DROP FKs:
• Bulk data loads (Data Pump, SQL*Loader, INSERT /*+ APPEND */): Disable constraints before load, validate and re-enable after.
ALTER TABLE child_table DISABLE CONSTRAINT fk_child_parent;

... load ...

ALTER TABLE child_table ENABLE NOVALIDATE CONSTRAINT fk_child_parent; -- re-enable without validating old data
• When application enforces RI at code level and FK overhead is proven to be a bottleneck (benchmark required).
• Partition exchange operations: Target partition must have constraints disabled.

ORACLE-SPECIFIC: RELY constraint — tell the optimizer to trust RI exists (for query rewrite/star transformation) without actually enforcing it. USE WITH CAUTION:

ALTER TABLE child_table MODIFY CONSTRAINT fk_child RELY DISABLE NOVALIDATE;


BEST PRACTICE: Never permanently remove FKs without a formal data governance decision. The performance gain rarely justifies the data integrity risk.

TECHNICAL Partition Design for DLM
Q10: How do you design for Oracle's partitioning to support both data lifecycle management and query performance?
▼ Show Model Answer

Partitioning for Data Lifecycle Management (DLM) requires aligning the partition strategy with both business retention policies and query access patterns.


DLM-OPTIMIZED PARTITION DESIGN:

RANGE by DATE (most common for DLM):

• Partition by MONTH or QUARTER: PARTITION BY RANGE (transaction_date) INTERVAL (NUMTOYMINTERVAL(1,'MONTH'))
• Enables: DROP PARTITION (instant, no undo), EXCHANGE PARTITION (archive to cold storage), COMPRESS older partitions.

TIERED COMPRESSION STRATEGY:
• Current month: NOCOMPRESS (frequent updates — no compression overhead)
• 3–12 months: COMPRESS FOR OLTP (block-level compression, allows DML)
• 12+ months: COMPRESS FOR ARCHIVE HIGH (maximum compression, read-only)
• ALTER TABLE sales MODIFY PARTITION p_2023_01 COMPRESS FOR ARCHIVE HIGH;

ILM (Information Lifecycle Management) — 12c+:
• Define automatic movement policies based on data age or access patterns:
ALTER TABLE sales ILM ADD POLICY ROW STORE COMPRESS ADVANCED SEGMENT AFTER 6 MONTHS OF NO MODIFICATION;
• Oracle ADO (Automatic Data Optimization) enforces policies automatically.

PARTITION PRUNING FOR PERFORMANCE:
• Queries MUST include the partition key in WHERE clause for pruning to work.
• Verify pruning: EXPLAIN PLAN — look for 'PARTITION RANGE SINGLE' or 'PARTITION RANGE ITERATOR'.
• Partition-wise joins: When both sides of a join are equi-partitioned on the join key, Oracle can join partition-to-partition in parallel (massive speedup for DW joins).

GLOBAL vs. LOCAL INDEXES:
• LOCAL index: One index per partition — moves with partition, supports partition operations without index rebuild. PREFERRED for most scenarios.
• GLOBAL index: Spans all partitions — becomes UNUSABLE after DROP/TRUNCATE partition unless ALTER TABLE ... UPDATE GLOBAL INDEXES is used (expensive).
• Rule: Prefer local indexes; use global only when queries frequently access data across many partitions on non-partition-key columns.

TECHNICAL GoldenGate Architecture
Q1: Explain the GoldenGate architecture — Extract, Trail Files, Data Pump, Replicat, and Manager.
▼ Show Model Answer

GoldenGate is a log-based change data capture (CDC) replication solution that works at the transaction log level.


COMPONENTS:

MANAGER (MGR): The controller process. Manages GoldenGate processes, port assignments, trail file purging, and process monitoring. Must run on both source and target. Start first: START MANAGER.


EXTRACT: Reads changes directly from the Oracle redo/archive logs (Integrated Capture) or from the database itself (Classic Capture).

• Primary Extract: Captures committed transactions from redo logs in near real-time. Writes to local trail files.
• Data Pump Extract: Secondary Extract that reads local trails and sends to remote trail on target system. Provides buffering — if network fails, trails accumulate locally; Pump resumes when connectivity restored.

TRAIL FILES: Sequential files of captured transactions. Format: .aa, .ab, ... Stored in $GG_HOME/dirdat/.

• Local trail: Source system (captured by Extract, read by Data Pump).
• Remote trail: Target system (written by Data Pump, read by Replicat).
• Retention: Configure PURGEOLDEXTRACTS in Manager parameter file.

REPLICAT: Reads trail files on the target and applies transactions to the target database using SQL or direct bulk apply.

• Classic Replicat: Single-threaded, sequential apply.
• Integrated Replicat (12c+): Leverages Oracle's apply engine (LOGMINER-based). Supports parallelism, dependency tracking, in-order apply. Most performant for Oracle-to-Oracle.
• Parallel Replicat (12.3+): Multiple Replicat processes coordinated by a coordinator. Massively improves throughput for large environments.

PROCESS FLOW: Source DB → Redo Log → Extract → Local Trail → Data Pump → Network → Remote Trail → Replicat → Target DB

TECHNICAL Integrated vs Classic Capture
Q2: What is Integrated Capture vs. Classic Capture in GoldenGate? When would you use each?
▼ Show Model Answer
CLASSIC CAPTURE (legacy):
• GoldenGate Extract reads Oracle redo/archive logs directly using its own log reader.
• Works outside the database kernel — no database dependency for log reading.
• Supports older Oracle versions (10g, 11g).
• Must handle redo log management manually (ensure archive logs retained until Extract processes them).
• DISADVANTAGE: Cannot capture all data types; struggles with some compressed/encrypted data; more susceptible to ORA errors during log reads.

INTEGRATED CAPTURE (12c+, recommended):
• Extract registers with Oracle's LogMiner-based infrastructure (mining server) inside the database.
• Oracle Database mines the redo logs and delivers LCRs (Logical Change Records) directly to Extract.
• ADVANTAGES:

- Supports all Oracle data types including XMLType, ANYDATA, abstract types.

- Better performance — parallel mining by the database itself.

- Works with online redo logs (no archive lag), RAC logs automatically.

- Supports Oracle-level supplemental logging management.

- Compatible with Oracle TDE (can mine encrypted redo).

- Works with CDB/PDB architecture (12c+).

• DISADVANTAGE: Requires ENABLE_GOLDENGATE_REPLICATION=TRUE DB parameter; adds small overhead to database.

SETUP:

Classic: EXTRACT ext1, SOURCEDB ..., LOGALLSUPCOLS ...

Integrated: EXTRACT ext1, INTEGRATED TRANLOGOPTIONS INTEGRATEDPARAMS (max_sga_size 512)


USE CASES:
• Classic: Older Oracle versions; cross-platform (non-Oracle to Oracle).
• Integrated: Oracle-to-Oracle 12c+; complex data types; CDB/PDB; high-throughput requirements.
TECHNICAL Initial Load
Q3: How do you perform an initial data load with GoldenGate while keeping ongoing replication in sync?
▼ Show Model Answer

The initial load synchronizes the target with the source before starting ongoing (change) replication. The challenge: changes continue flowing on the source during the load.


METHOD 1 — File-to-Replicat (GoldenGate native):

1. Start Extract with ADD EXTRACT ext1 BEGIN NOW — capture a starting CSN/SCN.

2. Run initial load Extract (EXTRACT extload, SOURCEISTABLE) to export all rows to trail files.

3. Start load Replicat to apply all initial rows to target.

4. After load complete: start change Replicat from the CSN captured in step 1 — applies all changes that occurred DURING the load.

5. Replicat catches up; ongoing replication takes over.


METHOD 2 — Oracle DataPump + GoldenGate:

1. Get consistent SCN: expdp ... FLASHBACK_SCN=<scn>

2. Configure Extract to start from that SCN: ADD EXTRACT ext1 SCN <scn>

3. Import DataPump export to target.

4. Start GoldenGate change Replicat from the same SCN.

5. All changes since the DataPump export SCN are applied by GoldenGate.


METHOD 3 — RMAN backup + GoldenGate (large databases):

1. RMAN backup of source with consistent SCN recorded.

2. Restore to target via RMAN.

3. GoldenGate Extract starts from backup SCN.

4. Apply all redo changes to target while Replicat catches up.


SUPPLEMENTAL LOGGING: Must be enabled BEFORE starting initial load:

ALTER DATABASE ADD SUPPLEMENTAL LOG DATA; (minimal, required)

ALTER DATABASE ADD SUPPLEMENTAL LOG DATA FOR PRIMARY KEY, UNIQUE, FOREIGN KEY COLUMNS; (recommended)


VERIFY SYNC: Use GGSCI STATS command; compare row counts; use GGSCI VERIFY command.

TECHNICAL Conflict Resolution
Q4: How does GoldenGate handle conflicts in bidirectional/multi-master replication?
▼ Show Model Answer

In bidirectional or multi-master replication, the same row can be updated on multiple sites simultaneously — creating conflicts.


CONFLICT TYPES:
• Update-Update conflict: Same row updated on two sites simultaneously.
• Insert-Insert conflict: Same PK inserted on two sites.
• Delete-Update conflict: Row deleted on one site while updated on another.
• Update-Delete conflict: Same scenario reversed.

CONFLICT DETECTION: GoldenGate detects by comparing before-image values in the trail with current target state. If they don't match, a conflict exists.


RESOLUTION STRATEGIES (in REPLICAT parameter file):

TIMESTAMP-BASED (most common): Last write wins based on timestamp.

RESOLVECONFLICT (UPDATE, (DEFAULT, USEMAX (update_timestamp)), UPDATEROWEXISTS);


SOURCE-PRIORITY: One site always wins.

RESOLVECONFLICT (UPDATE, (DEFAULT, USEDELTA (num_col)), UPDATEROWEXISTS);


DELTA (ADDITIVE): For numeric columns, apply the difference rather than the value.

Useful for: inventory quantities, account balances that may be adjusted concurrently.


CUSTOM RESOLUTION via CDRs (Conflict Detection and Resolution):

• Write a stored procedure or external procedure to handle complex business logic.
• REPERROR (DEFAULT, EXCEPTION_HANDLER) routes conflicts to a handler procedure.

ERROR LOGGING: Unconflicted errors go to DISCARD file; logged for review and manual resolution.


BEST PRACTICE:
• Design application to minimize conflicts — route writes for an entity to a single site where possible (partitioned active-active).
• Use sequences with non-overlapping ranges on each site to prevent PK conflicts.
• Monitor GGSERR.LOG and discard files daily in multi-master environments.

TECHNICAL Migration with GGS
Q6: How would you use GoldenGate for a zero-downtime Oracle database migration?
▼ Show Model Answer

GoldenGate enables zero-downtime (or near-zero-downtime) migrations by maintaining continuous replication between source and target while traffic is gradually shifted.


MIGRATION SCENARIOS WHERE GGS IS IDEAL:
• Oracle version upgrade (e.g., 12c → 19c) with different platforms/OS.
• Cross-platform migration (Linux to AIX, Solaris to Linux).
• Migration to Oracle Cloud (OCI) or Exadata.
• Database consolidation (multiple source DBs → single target CDB).

HIGH-LEVEL ZERO-DOWNTIME MIGRATION PROCESS:
Phase 1 — Setup Replication:

1. Enable supplemental logging on source.

2. Configure GoldenGate on source and target.

3. Start Extract; capture starting SCN.

4. Perform initial load (DataPump export from SCN / RMAN restore).

5. Start Replicat; apply all changes since initial load SCN.


Phase 2 — Validation (run in parallel):

6. Verify data consistency: row counts, checksums, GGS VERIFY command.

7. Run application test suite against target database.

8. Monitor GGS lag — ensure target is < 5 seconds behind source.


Phase 3 — Cutover (minimal downtime window):

9. Schedule cutover window (even 30 seconds is achievable).

10. Stop application writes to source.

11. Wait for GGS lag to reach 0 seconds (all changes applied to target).

12. Stop Extract and Replicat.

13. Update application connection strings / DNS / load balancer to point to target.

14. Restart application against target.

15. Total cutover time: 30 seconds to 5 minutes depending on infrastructure.


Phase 4 — Validation & Rollback:

16. Keep source live and GGS available for up to 48 hours for rollback capability.

17. If issues: switch connection strings back to source; restart GGS in reverse direction.


GGS BIDIRECTIONAL (ROLLBACK CAPABILITY): Configure temporary reverse replication from target → source so any changes made to target after cutover can be synced back if rollback is needed.

TECHNICAL Trail File Management
Q7: What are GoldenGate trail files — how are they managed and what happens if they fill up?
▼ Show Model Answer

Trail files are the heart of GoldenGate — sequential binary files containing captured transactions in a proprietary format.


TRAIL FILE DETAILS:
• Default location: $GG_HOME/dirdat/
• Naming: Two-letter prefix + sequence number: aa000001, aa000002, ...
• Default size: 500MB (configurable with MAXFILESIZE in Extract parameter).
• Format: Binary; contains before/after images of all captured columns plus metadata (SCN, commit timestamp, operation type, table name).

TRAIL FILE LIFECYCLE:

1. Extract writes to trail; when it reaches MAXFILESIZE, closes it and starts a new one.

2. Data Pump reads closed trail files and sends them to the remote system.

3. Replicat reads remote trail files and applies to target.

4. After Replicat processes a trail file and checkpoints past it, it can be purged.


PURGE CONFIGURATION (in Manager parameter file):

PURGEOLDEXTRACTS ./dirdat/aa, USECHECKPOINTS, MINKEEPDAYS 3, MAXKEEPDAYS 7

• USECHECKPOINTS: Only purge trails that ALL Replicats have read past.
• MINKEEPDAYS: Keep at least 3 days regardless of checkpoints (for recovery/debugging).

WHAT HAPPENS IF TRAIL FILES FILL THE DISK:

1. Extract ABENDS (stops) — cannot write new records.

2. Source database is NOT affected — GoldenGate is decoupled from source DB operations.

3. Archive logs on source may start accumulating (need to be retained until Extract catches up).

4. RESOLUTION: Free disk space; restart Extract (it resumes from last checkpoint).


MONITORING TRAIL DISK USAGE:

INFO EXTRACT EXT1 DETAIL — shows trail file info and disk usage.

Automate alerts when dirdat/ exceeds 70% of filesystem capacity.


BEST PRACTICE: Dedicate a filesystem to GoldenGate trail files; size it for 48–72 hours of change volume.

TECHNICAL Filtering & Transformation
Q8: How do you configure GoldenGate filtering and column transformation?

• @DATE, @DATENOW, @TIMESTAMP — date conversions

MAP source.sales TO target.sales_usd,

COLMAP (sale_id = sale_id,

sale_quarter = @CASE(MONTH(sale_date), 1,2,3,'Q1', 4,5,6,'Q2', 7,8,9,'Q3', 'Q4'),

TOKEN-BASED (passing metadata):

Q10: How do you configure GoldenGate for Oracle CDB/PDB (multitenant) environments?
▼ Show Model Answer

GoldenGate's behavior with Multitenant (CDB/PDB) architecture differs significantly from non-CDB setups.


CAPTURE OPTIONS FOR CDB:

Option 1 — CDB-Level Extract (Integrated Capture at CDB root):

• Requires C##GGADMIN common user with GoldenGate privileges in CDB.

Option 2 — PDB-Level Classic Capture (12.2+):

• Extract connects directly to a PDB (not CDB root).
• EXTRACT ext1, SOURCEDB pdb1@host:1521/pdb1
• More granular; can have separate GG homes per PDB team.
• DISADVANTAGE: Classic capture only (not integrated); cannot mine CDB root redo directly.

• USERIDALIAS ggadmin DOMAIN OracleGoldenGate
• MAP pdb1.hr.employees TO pdb2.hr.employees; (cross-PDB replication)

SUPPLEMENTAL LOGGING IN CDB: Enable at PDB level:

ALTER SESSION SET CONTAINER=pdb1; ALTER DATABASE ADD SUPPLEMENTAL LOG DATA; EXEC DBMS_GOLDENGATE_AUTH.GRANT_ADMIN_PRIVILEGE('C##GGADMIN', CONTAINER=>'ALL');

PDB-LEVEL CONTROL: Individual PDBs can enable/disable GG capture independently.


GOTCHA: Container database redo logs contain interleaved redo for ALL PDBs — Extract must filter by PDB con_id internally; this is handled automatically by integrated capture.

SCENARIO Missing Archive Log
SCENARIO: GoldenGate Extract is in ABEND state with error 'OGG-00446 Missing archive log'. The log needed is sequence 5821. How do you resolve this?
▼ Show Model Answer

This is one of the most common GoldenGate crises. The Extract needs archive log sequence 5821 to continue, but it has been deleted (possibly by RMAN or an aggressive archive log purge policy).


ASSESSMENT:

1. Confirm which log is needed: VIEW REPORT EXT1 — shows exact sequence and thread.

2. Check if log still exists anywhere: RMAN> LIST ARCHIVELOG ALL; or ls on archive log directories.

3. Check RMAN catalog/backup: RMAN> LIST BACKUP OF ARCHIVELOG SEQUENCE 5821 THREAD 1;


IF ARCHIVE LOG EXISTS SOMEWHERE:
• Copy or restore to Extract's accessible location.
• Register if needed: ALTER DATABASE REGISTER LOGFILE '...';
• Restart Extract: START EXTRACT EXT1 — it will find and process the log.

IF ARCHIVE LOG IS PERMANENTLY LOST (most common in production crisis):

You must decide: how much data loss is acceptable?


Option A — Re-synchronize (data loss accepted for GGS meta; target may be out of sync):

1. Note the current SCN on source: SELECT CURRENT_SCN FROM V$DATABASE;

2. Stop and delete Replicat: STOP REPLICAT REP1; DELETE REPLICAT REP1;

3. Re-do initial load from current SCN; re-configure Extract from NOW.

4. ALTER EXTRACT EXT1 BEGIN NOW;


Option B — Position past the gap (accept possible missed transactions):

ALTER EXTRACT EXT1 ETROLLOVER; -- start new trail; move past gap

Or: DELETE EXTRACT EXT1; re-add with newer SCN.

WARNING: Target database may now be inconsistent with source — must validate data.


PREVENTION (critical lesson): Set RMAN ARCHIVELOG RETENTION POLICY to keep archive logs at least 2× GoldenGate's typical lag, or use CONFIGURE ARCHIVELOG DELETION POLICY TO APPLIED ON STANDBY to prevent premature deletion.

TECHNICAL Incremental Backups
Q1: Explain the difference between RMAN Level 0 and Level 1 incremental backups and how Block Change Tracking improves them.
▼ Show Model Answer
INCREMENTAL BACKUP LEVELS:

LEVEL 0 (Base Backup): Backs up ALL data blocks that have ever been used (equivalent to a full backup but used as the base for incrementals). Does NOT back up never-written blocks.


LEVEL 1 CUMULATIVE: Backs up all blocks changed since the LAST Level 0 backup.

• Recovery: Level 0 + LATEST Level 1 cumulative. Fewer pieces to merge.
• More data backed up per Level 1 run than differential.
• PREFERRED for most environments — simpler recovery.

LEVEL 1 DIFFERENTIAL: Backs up only blocks changed since the LAST backup (Level 0 OR Level 1).

• Recovery: Level 0 + EVERY Level 1 differential since Level 0.
• Each backup is smaller, but recovery applies more pieces.

TYPICAL SCHEDULE (cumulative):

Sunday: BACKUP INCREMENTAL LEVEL 0 DATABASE;

Mon–Sat: BACKUP INCREMENTAL LEVEL 1 CUMULATIVE DATABASE;


BLOCK CHANGE TRACKING (BCT):

Without BCT: RMAN must scan every data block header to find changed blocks — I/O intensive for large databases.

With BCT: A change tracking file (binary) records which blocks changed after each backup. RMAN reads only this file to identify changed blocks → dramatically faster Level 1 backups.


ENABLE BCT:
ALTER DATABASE ENABLE BLOCK CHANGE TRACKING USING FILE '/ora/change_track.f'; -- Or in FRA: ALTER DATABASE ENABLE BLOCK CHANGE TRACKING; (automatic naming)

VERIFY: SELECT status, filename, bytes FROM v$block_change_tracking;


PERFORMANCE IMPACT: BCT reduces Level 1 backup time by 70–90% for large databases. Small overhead on database writes to update the tracking file (negligible for most workloads).


RMAN QUERY: RMAN> LIST BACKUP SUMMARY; — see backup sizes; compare Level 0 vs Level 1 sizes to verify BCT is working.

TECHNICAL PITR Procedures
Q2: Walk me through Point-in-Time Recovery (PITR) for a tablespace and for the whole database.
▼ Show Model Answer

POINT-IN-TIME RECOVERY restores the database or a tablespace to a specific past point (by time, SCN, or restore point).


DATABASE PITR (incomplete recovery):
RMAN> STARTUP MOUNT; RMAN> RUN {

SET UNTIL TIME "TO_DATE('2024-03-15 14:30:00','YYYY-MM-DD HH24:MI:SS')";

-- OR: SET UNTIL SCN 12345678; -- OR: SET UNTIL RESTORE POINT my_restore_point;

RESTORE DATABASE;

RECOVER DATABASE;

}

RMAN> ALTER DATABASE OPEN RESETLOGS; -- REQUIRED after incomplete recovery

TSPITR — Tablespace Point-in-Time Recovery (12c+ in CDB: PITR per PDB):

Recovers ONE tablespace to a past point without affecting the rest of the database.

Requirement: The tablespace must be self-contained (no dependencies on other tablespaces that changed).


Check self-containment:

EXEC DBMS_TTS.TRANSPORT_SET_CHECK('SALES_TS', TRUE);

SELECT * FROM transport_set_violations; -- must be empty


PERFORM TSPITR:
RMAN> RECOVER TABLESPACE sales_ts UNTIL TIME "TO_DATE('2024-03-15 14:30:00','YYYY-MM-DD HH24:MI:SS')"

AUXILIARY DESTINATION '/tmp/tspitr_aux';


RMAN creates an AUXILIARY database internally, recovers the tablespace to the target point, and exports it back to the production database. The auxiliary destination needs sufficient space for the recovered tablespace.


POST-TSPITR: Tablespace is ONLINE; application can immediately use recovered data.


CDB/PDB PITR (12.2+):
RMAN> RECOVER PLUGGABLE DATABASE pdb1 UNTIL SCN 99999999;

-- Recovers a single PDB to a point; other PDBs unaffected. Requires CDB closed for PDB recovery.


BEST PRACTICE: Document the exact SCN at which critical events happened — data loads, batch completions — so PITR targets are known in advance.

TECHNICAL RMAN Duplication
Q3: How do you perform RMAN database duplication? Compare connected vs. backup-based duplication.
▼ Show Model Answer

RMAN DUPLICATE creates a copy of a database — used for creating test/dev environments, migrating to new servers, or creating DataGuard standbys.


CONNECTED DUPLICATION (ACTIVE DATABASE DUPLICATE):
• Source and auxiliary (destination) databases must be reachable from the RMAN client simultaneously.
• RMAN reads data blocks directly from the source database's buffer cache via network.
• No backup required — copies the live database.
• Fastest for smaller databases; slightly higher impact on source.

RMAN> CONNECT TARGET sys@source_db; RMAN> CONNECT AUXILIARY sys@aux_db; RMAN> DUPLICATE TARGET DATABASE TO auxdb

FROM ACTIVE DATABASE

SPFILE PARAMETER_VALUE_CONVERT ('source_db','auxdb','/old/path','/new/path')

NOFILENAMECHECK;


BACKUP-BASED DUPLICATION:
• Auxiliary instance connects to RMAN; source database can be offline or unreachable.
• RMAN uses existing backup sets and archive logs.
• Required when: source DB is down, network bandwidth insufficient for active dup, creating standby from backup.

RMAN> CONNECT TARGET /; -- source or catalog RMAN> CONNECT AUXILIARY sys@aux_db; RMAN> DUPLICATE TARGET DATABASE TO auxdb

BACKUP LOCATION '/backup/path'

SPFILE ... NOFILENAMECHECK;


FOR DATAGUARD STANDBY CREATION:
RMAN> DUPLICATE TARGET DATABASE FOR STANDBY FROM ACTIVE DATABASE DORECOVER;

-- DORECOVER: Recovers all available redo after duplication; leaves standby ready for MRP.


PRE-REQUISITES FOR ANY DUPLICATION:
• Auxiliary instance started with STARTUP NOMOUNT and minimal spfile (db_name, control_files only).
• Sufficient disk space on auxiliary.
• Oracle Net connectivity configured.
• Matching Oracle version/patch level (or at minimum compatible version for standby).

SCRIPTS: Store duplication scripts in RMAN catalog (STORE SCRIPT); run with EXECUTE SCRIPT for repeatability.

TECHNICAL Retention Policies
Q4: What are the RMAN retention policies and how do you configure and verify them?
▼ Show Model Answer

RMAN retention policy defines how long backups must be kept before they can be considered obsolete and eligible for deletion.


POLICY TYPES:

RECOVERY WINDOW: Keep backups sufficient to recover to any point within the past N days.

RMAN> CONFIGURE RETENTION POLICY TO RECOVERY WINDOW OF 7 DAYS;
• RMAN marks a backup obsolete only when it's no longer needed to recover to any point in the last 7 days.
• Means: enough backups to perform PITR to 7 days ago must exist.
• Automatically keeps sufficient archive logs to support the recovery window.

REDUNDANCY: Keep N copies of each backup. Older copies become obsolete when N newer copies exist.

RMAN> CONFIGURE RETENTION POLICY TO REDUNDANCY 3;
• Simpler to manage; less nuanced than recovery window.
• Regardless of time — just maintains 3 copies of each backup piece.

CLEARING: CONFIGURE RETENTION POLICY CLEAR; — removes policy (reverts to REDUNDANCY 1 default).


NONE: CONFIGURE RETENTION POLICY TO NONE; — RMAN never marks backups obsolete. Dangerous for disk space.


CHECKING OBSOLETE BACKUPS:
RMAN> REPORT OBSOLETE; -- what would be deleted? RMAN> DELETE OBSOLETE; -- actually delete
CROSSCHECKING CATALOG vs. ACTUAL DISK:
RMAN> CROSSCHECK BACKUP; -- updates catalog to reflect what's actually on disk/tape RMAN> DELETE EXPIRED BACKUP; -- remove catalog entries for backups no longer on disk

ARCHIVELOG RETENTION: Separate from backup retention — controls when archive logs can be deleted.

RMAN> CONFIGURE ARCHIVELOG DELETION POLICY TO BACKED UP 1 TIMES TO DISK; -- only delete after backed up once RMAN> CONFIGURE ARCHIVELOG DELETION POLICY TO APPLIED ON STANDBY; -- for DataGuard environments

MONITORING: V$RMAN_BACKUP_JOB_DETAILS, RC_BACKUP_JOB_DETAILS (catalog), V$RMAN_STATUS.

TECHNICAL Datafile Recovery
Q6: How do you restore a single datafile that was accidentally deleted in a production database?
▼ Show Model Answer

Accidentally deleted datafiles while the database is running are more recoverable than most people think — because Oracle keeps the file descriptor open.


IMMEDIATE ASSESSMENT:

1. If database is RUNNING and the tablespace is still accessible — the OS has the file open (via Oracle process). Do NOT restart the database. Data is still readable in memory (buffer cache).

2. Check: SELECT file#, name, status FROM v$datafile; — look for the missing file.

3. On Linux: lsof | grep deleted_filename — shows the file still held open by Oracle's process.

Copy the deleted file back from /proc/<pid>/fd/<fd_number> to its original location. (Linux only — file is recoverable while database stays up.)


RMAN ONLINE DATAFILE RECOVERY (tablespace can stay online in some cases):

-- Take the affected datafile offline (if needed):

ALTER DATABASE DATAFILE '/path/missing_file.dbf' OFFLINE;

RESTORE DATAFILE '/path/missing_file.dbf';

RECOVER DATAFILE '/path/missing_file.dbf';

}

ALTER DATABASE DATAFILE '/path/missing_file.dbf' ONLINE;


FOR SYSTEM, UNDO, or ACTIVE DATAFILES:
• Cannot take SYSTEM tablespace offline — must restore with database in MOUNT state.
RMAN> STARTUP MOUNT; RESTORE DATABASE; RECOVER DATABASE; ALTER DATABASE OPEN;

FOR RECENTLY CREATED DATAFILE (added after last backup):

• No backup exists for this file → must drop and recreate the tablespace/datafile.
• If data was loaded: need to reload from source system or use Flashback if tablespace was not new.

ASM ENVIRONMENTS:
• ASM redundancy (NORMAL/HIGH disk groups) automatically rebalances lost data — no action needed if disk group survives.
• If entire ASM disk group lost: RMAN restore is the path.

PREVENTION: Never use 'rm' on Oracle-managed files. Use RMAN DROP DATAFILE or ALTER DATABASE DATAFILE OFFLINE DROP. Monitor filesystem and ASM alerts.

TECHNICAL HugePages Configuration
Q2: Explain HugePages — how to calculate the correct value and why it matters for Oracle.
▼ Show Model Answer

WHAT ARE HUGEPAGES: Linux's standard memory page size is 4KB. HugePages uses 2MB pages. For Oracle SGA (often 10–500GB), using 4KB pages means millions of page table entries — consuming significant CPU and memory just to manage the SGA mapping.


WHY HUGEPAGES FOR ORACLE:
• Dramatically reduces page table size (1GB SGA: 262,144 pages at 4KB vs. 512 pages at 2MB).
• Pages are LOCKED in memory (no swapping) — SGA cannot be swapped out to disk.
• Eliminates TLB (Translation Lookaside Buffer) pressure for large SGA systems.
• Required for memory > 16GB SGA on many Linux configurations.
• Reduces kernel overhead for memory management.

CALCULATING HUGEPAGES NEEDED:

1. Determine total SGA size (across ALL database instances on the host):

SELECT sum(value)/1024/1024/1024 FROM gv$sga WHERE name='Fixed SGA Size' OR name='Variable Size' OR name='Database Buffers' OR name='Redo Buffers'; -- Or simply: sum of SGA_TARGET + SGA_MAX_SIZE for all instances on the host.

2. Calculate number of HugePages:

hugepages_needed = CEIL(Total_SGA_in_bytes / 2097152) # 2MB = 2097152 bytes

Add 10% buffer: hugepages_needed = hugepages_needed * 1.1


3. Set in /etc/sysctl.conf:

vm.nr_hugepages = <calculated_value>

sysctl -p && service oracle restart

4. Verify allocation:

grep -i huge /proc/meminfo

HugePages_Total: 5120

HugePages_Free: 4608 # Free pages; if HugePages_Free = 0, SGA not fully mapped


ORACLE CONFIGURATION:
• AMM (Automatic Memory Management with MEMORY_TARGET) is INCOMPATIBLE with HugePages — Oracle uses /dev/shm (tmpfs) for AMM which cannot use HugePages.
• Use SGA_TARGET + PGA_AGGREGATE_TARGET instead of MEMORY_TARGET when HugePages is required.

TRANSPARENT HUGEPAGES (THP): Oracle recommends DISABLING THP — it causes latency spikes.

echo never > /sys/kernel/mm/transparent_hugepage/enabled && echo never > /sys/kernel/mm/transparent_hugepage/defrag

Make persistent in rc.local or tuned profile.

TECHNICAL Storage & FS Tuning
Q5: How do you configure and tune disk I/O schedulers and file systems for Oracle on Linux?
▼ Show Model Answer

I/O SCHEDULER SELECTION (for spinning disks — not relevant for NVMe/SSD which have hardware queuing):

• DEADLINE (recommended for Oracle on spinning disks): Prioritizes reads, limits write starvation, bounded latency.
echo deadline > /sys/block/sda/queue/scheduler
• CFQ (default): Fair queuing — good for general workloads, not optimal for Oracle's mixed read/write patterns.
• NOOP: No sorting; best for SSDs and SANs with hardware RAID (which do their own scheduling).
echo noop > /sys/block/sda/queue/scheduler
• Persist: Add to udev rules or /etc/rc.local.

READ-AHEAD:
• Default Linux read-ahead (256 sectors = 128KB) is appropriate for most Oracle OLTP.
• For large sequential I/O (DW, backups): increase: blockdev --setra 8192 /dev/sdb (8192 * 512B = 4MB read-ahead).
• For pure random OLTP: reduce read-ahead: blockdev --setra 0 /dev/sdb.

FILESYSTEM CHOICES:
• ext4: Default; good all-around; journaling protects metadata.
• XFS (recommended for large Oracle files): Better performance for large files, pre-allocated extents reduce fragmentation; better parallel I/O.
• Oracle ACFS: Oracle's clustered filesystem for RAC shared storage (non-datafile files).
• ASM (preferred for datafiles): Not a traditional FS; Oracle's own storage manager. Striping + mirroring without OS FS layer.

KEY MOUNT OPTIONS (for ext4/XFS with Oracle datafiles):

/dev/sdb /u01 xfs defaults,noatime,nodiratime,nobarrier 0 0

• noatime: Don't update access time on reads — reduces write I/O for metadata.
• nodiratime: Same for directories.
• nobarrier: Disable write barriers if battery-backed write cache exists (improves write performance; DANGEROUS without BBU).
• relatime (safer alternative to noatime): Updates atime only when mtime is newer.

NUMA CONFIGURATION:
• Non-Uniform Memory Access: Oracle on multi-socket servers benefits from NUMA-aware configuration.
• numad: Auto-NUMA balancing daemon — disable in favor of Oracle's internal NUMA management.
• Add --interleave=all to Oracle startup (oracle user's shell profile) for SGA distribution across NUMA nodes.

numactl --interleave=all $ORACLE_HOME/bin/oracle ... (in oraenv startup).

TECHNICAL Load Average Analysis
Q6: How do you troubleshoot high load average on an Oracle Linux server even when CPU utilization is low?
▼ Show Model Answer

Load average measures the number of processes in RUNNING or WAITING state (for CPU or I/O). High load with low CPU = processes waiting for something other than CPU (most commonly I/O or locks).


TOOLS FOR DIAGNOSIS:

1. vmstat 1 10 — check 'b' column (processes blocked waiting for I/O):

> procs: r=2, b=15 → 15 processes blocked — I/O issue.


2. iostat -x 1 — identify saturated disks (already covered in Q3).


3. Check D-state processes (stuck in uninterruptible sleep — always I/O/NFS wait):

ps aux | awk '$8 ~ /D/ {print $0}'

D state processes contribute to load average but cannot be killed with kill -9.


4. sar -q 1 10 — historical load average tracking.


5. sar -d 1 10 — device I/O statistics.


6. strace on the stuck process (if safe): strace -p <pid> — shows which syscall it's waiting in.

'read()' or 'pread64()' stuck = I/O wait.


7. lsof | grep <oracle_pid> — which files the process has open (which datafile is causing the wait).


8. For NFS mounts causing D-state: check nfsstat -c, mount options (hard vs. soft mounts).

Oracle should NEVER use hard NFS mounts without proper timeout configuration.


ORACLE-SPECIFIC CHECK:
• Cross-correlate with ASH: SELECT session_id, session_state, event, sql_id

FROM v$active_session_history WHERE session_state='WAITING' AND wait_class='User I/O' AND sample_time > SYSDATE - 5/1440;


COMMON RESOLUTIONS:
• I/O saturation → spread datafiles, add storage, upgrade to SSD.
• NFS issues → switch to local storage or ASM.
• Memory pressure causing swapping → check free -m; add RAM; tune SGA/PGA; verify HugePages configured.

TECHNICAL AWR Report Interpretation
Q1: How do you read and interpret an AWR report? What are the key sections and what do you look for first?
▼ Show Model Answer

AWR (Automatic Workload Repository) report is the primary Oracle performance diagnostic tool. Reading it systematically is essential.


READING ORDER (top-down priority):

1. REPORT HEADER: DB version, host, snapshot interval, RAC instance. Confirm the time window covers the problem period.


2. REPORT SUMMARY — DB TIME AND LOAD PROFILE:

DB Time / Elapsed Time = Active Session Count equivalent. If 1 CPU, 60 min elapsed, DB Time > 60 min = overloaded.

Load Profile: Logical reads/s, physical reads/s, executions/s, parse rate, redo size/s.

LOOK FOR: High parse/execute ratio (< 1:10 = parse problem); high physical reads (I/O); high redo = high write activity.


3. TOP WAIT EVENTS (most important section):

Shows where the database is spending non-CPU time. Top 5 events tell the story.

COMMON WAITS AND MEANING:

• "db file sequential read" — single block I/O (index scans) — possible plan issue or I/O saturation.

• "db file scattered read" — multiblock I/O (FTS) — full table scans running.

• "log file sync" — commit waits for LGWR — slow redo log writes; too frequent commits.

• "latch: shared pool" — shared pool contention; non-shared SQL / library cache pressure.

• "buffer busy waits" — hot blocks; multiple sessions reading/modifying same block.

• "gc cr block receive time" (RAC) — Cache Fusion latency; interconnect issue or hot blocks.

• "enq: TX - row lock contention" — application-level row locking; blocking sessions.


4. SQL ORDERED BY (various metrics): Top SQL by elapsed time, CPU time, disk reads, executions.

Compare: If top SQL by elapsed ≠ top SQL by CPU → wait-heavy SQL (I/O or lock waits).


5. INSTANCE EFFICIENCY: Buffer cache hit %, soft parse %, library cache hit %, in-memory sort %.

TARGETS: Buffer hit > 95%, soft parse > 95%, library cache > 99%.


6. MEMORY STATISTICS: SGA breakdown, buffer cache hit, PGA usage, top memory-consuming SQL.


7. I/O STATS: Reads/writes per file — identify hot datafiles.


QUICK TRIAGE: Top wait events → SQL causing those waits → fix the SQL or the resource.

TECHNICAL ASH Analysis
Q2: Explain ASH (Active Session History) — how does it work and how do you use it for ad-hoc performance analysis?
▼ Show Model Answer

ASH is a rolling in-memory buffer (V$ACTIVE_SESSION_HISTORY) that samples all active sessions every 1 second. A subset is written to disk in the AWR (DBA_HIST_ACTIVE_SESS_HISTORY) every 10 seconds.


HOW IT WORKS:
• MMON samples V$SESSION every 1 second for all sessions not in 'idle' wait.
• Captures: SQL_ID, event, wait_class, session_state (ON CPU vs WAITING), blocking_session, current_obj#.
• V$ASH: Last ~1 hour in memory; DBA_HIST_ASH: Historical (AWR retention period).
• No AWR license needed for V$ASH (current data); DBA_HIST_ASH requires Diagnostics Pack.

KEY ASH QUERIES:

1. Top wait events in the last 30 minutes:

SELECT event, count(*) samples, ROUND(count(*)/SUM(count(*)) OVER()*100,1) pct

FROM v$active_session_history

WHERE sample_time > SYSDATE - 30/1440 AND session_state='WAITING'

GROUP BY event ORDER BY 2 DESC;


2. Which SQL was causing most waits in a time range:

SELECT sql_id, count(*) waits, event

FROM dba_hist_active_sess_history

WHERE sample_time BETWEEN TO_DATE('2024-03-15 14:00','YYYY-MM-DD HH24:MI')

AND TO_DATE('2024-03-15 14:30','YYYY-MM-DD HH24:MI')

AND session_state='WAITING'

GROUP BY sql_id, event ORDER BY 2 DESC FETCH FIRST 10 ROWS ONLY;


3. Timeline of active sessions (identify peak):

SELECT TO_CHAR(sample_time,'HH24:MI') minute, count(*) active_sessions

FROM v$active_session_history WHERE sample_time > SYSDATE - 1/24

GROUP BY TO_CHAR(sample_time,'HH24:MI') ORDER BY 1;


4. Who was blocking whom:

SELECT h.session_id, h.blocking_session, h.event, h.sql_id, h.sample_time

FROM v$active_session_history h

WHERE h.blocking_session IS NOT NULL AND sample_time > SYSDATE - 30/1440;


ORADEBUG SHORTHAND: SELECT * FROM v$ash_info; — shows ASH buffer size and overflow rate.

TECHNICAL SQL Plan Management
Q4: Explain SQL Plan Management (SPM) — how to use it to stabilize execution plans.
▼ Show Model Answer

SPM prevents unexpected execution plan changes by maintaining a baseline of verified (accepted) plans for SQL statements. Only baseline plans are used by the optimizer; new plans must be verified before use.


PLAN BASELINE CONCEPTS:
• SQL Plan Baseline: A set of accepted plans for a SQL statement (identified by SQL_HANDLE).
• Accepted Plan: Used by optimizer. Marked ACCEPTED=YES, ENABLED=YES.
• Unaccepted Plan: Discovered but not yet verified. Not used until manually accepted.
• Fixed Plan: Only fixed plans are considered, regardless of better plans discovered.

CAPTURING BASELINES:

Method 1 — From cursor cache (reactive, for existing SQL):

SELECT DBMS_SPM.LOAD_PLANS_FROM_CURSOR_CACHE(sql_id => 'abc123') FROM dual;


Method 2 — Automatic capture (proactive):

ALTER SYSTEM SET OPTIMIZER_CAPTURE_SQL_PLAN_BASELINES=TRUE; -- captures all repeating statements

(Only recommended in specific tuning phases; can flood SYSAUX)


Method 3 — From AWR (historical):

SELECT DBMS_SPM.LOAD_PLANS_FROM_AWR(begin_snap => 1234, end_snap => 1236) FROM dual;


EVOLVING BASELINES (accepting better plans):

When a new plan is discovered that is faster, it starts as UNACCEPTED. Run evolution to verify and accept:

SET SERVEROUTPUT ON

DECLARE l_rpt CLOB;

BEGIN l_rpt := DBMS_SPM.EVOLVE_SQL_PLAN_BASELINE(sql_handle => 'SQL_abc123', verify => 'YES', commit => 'YES'); DBMS_OUTPUT.PUT_LINE(l_rpt); END;

/


FIXING A PLAN (prevent any other plan from being used):

UPDATE sys.sqlobj$SET flags=1 WHERE signature = (SELECT exact_matching_signature FROM dba_sql_plan_baselines WHERE sql_handle='SQL_abc123' AND plan_name='SQL_PLAN_abc123xxx');

-- Or use DBMS_SPM.ALTER_SQL_PLAN_BASELINE(sql_handle, plan_name, attribute_name=>'FIXED', attribute_value=>'YES');


MONITORING: DBA_SQL_PLAN_BASELINES, V$SQL (BASELINE_NAME column shows when a baseline is being used).

CLEANUP: DBMS_SPM.DROP_SQL_PLAN_BASELINE(sql_handle, plan_name) — remove obsolete baselines.

TECHNICAL Adaptive Query Optimization
Q5: What is Adaptive Query Optimization in Oracle 12c+ and how does it affect tuning?
▼ Show Model Answer

Adaptive Query Optimization (AQO) allows Oracle's optimizer to adapt execution plans and statistics-gathering strategies at runtime — based on actual data observed during query execution.


TWO MAIN COMPONENTS:

1. ADAPTIVE PLANS: The optimizer creates a plan with decision points (JOIN METHOD switches). During execution, STATISTICS COLLECTORS monitor row counts at key plan nodes. If actual rows differ significantly from estimates, the plan can switch to a better join method at runtime.

• Adaptive Join Methods: Switch between nested loop (expected low rows) and hash join (if row counts exceed threshold).
• EXPLAIN PLAN shows 'STATISTICS COLLECTOR' nodes in adaptive plans.
• V$SQL: IS_RESOLVED_ADAPTIVE_PLAN column shows if the plan adapted.
• Disable if causing instability: ALTER SESSION SET optimizer_adaptive_plans=FALSE;

2. ADAPTIVE STATISTICS: The optimizer uses additional statistics-gathering techniques automatically:

• Dynamic Statistics (replaces Dynamic Sampling): Oracle gathers statistics on small samples for tables with stale/missing stats.
• Automatic Reoptimization: After first execution, if actual rows differ from estimates, the query is reoptimized on subsequent runs using corrected cardinality estimates. This is the mechanism behind 'cardinality feedback.'
• SQL Plan Directives: When repeated cardinality misestimates are detected, Oracle creates a directive to always use extended statistics or dynamic sampling for that column combination. Stored persistently in SYSAUX.

View: DBA_SQL_PLAN_DIRECTIVES.


TUNING IMPLICATIONS:
• Adaptive plans explain why the same SQL may execute differently on first vs. subsequent runs.
• SQL Plan Directives can become stale — if underlying data distribution changes, old directives may cause poor plans. Flush stale directives: EXEC DBMS_SPM.FLUSH_SQL_PLAN_DIRECTIVES;
• AQO can cause plan instability in some environments — some DBAs disable with optimizer_adaptive_features=FALSE (12.1) or optimizer_adaptive_plans=FALSE + optimizer_adaptive_statistics=FALSE (12.2+).
• Test in dev/test before blanket disabling — AQO solves many cardinality estimation problems automatically.
TECHNICAL Log File Sync Waits
Q6: How do you analyze and resolve 'log file sync' wait events?
▼ Show Model Answer

'log file sync' is the wait a user session experiences between issuing COMMIT and receiving acknowledgement — because the user session must wait for LGWR to flush the redo buffer to the online redo log file.


CAUSES AND DIAGNOSIS:

1. Slow redo log I/O (most common):

Redo logs on slow storage — LGWR is slow to write.

CHECK: iostat -x shows high await for the redo log disk device.

V$FILESTAT or V$LOG where log_file_sync correlates with log_write_time.

FIX: Move redo logs to the fastest available storage (SSD/NVMe). Never on NFS. Never shared with high-write datafiles.


2. Redo log too small / too frequent switches:

Frequent log switches cause checkpoint pressure AND more frequent sync waits.

CHECK: SELECT to_char(FIRST_TIME,'HH24:MI') FROM v$log_history ORDER BY 1; — are switches every 2–3 min?

FIX: Increase redo log size (at minimum 500MB for busy OLTP; 1–2GB is common).


3. Too many commits (commit storm):

Application commits after every single row (e.g., COMMIT inside a loop).

CHECK: AWR Load Profile — commits/second.

FIX: Batch commits (commit every N rows, not every row). Educate developers.


4. ASYNC commit (workaround, not fix):

ALTER SESSION SET COMMIT_WRITE='BATCH,NOWAIT'; -- application doesn't wait for LGWR.

RISK: Small window of data loss on instance failure (last second of commits).

Use ONLY for non-critical, recoverable batch operations.


5. RAC-specific log file sync:

In RAC, each instance has its own redo logs. Cross-instance commits don't add overhead.

But: GCS (global cache service) log sync + instance-level log sync compounds latency.

Monitor: GV$LOG grouped by instance to identify which instance has the worst sync times.


QUICK CHECK QUERY:

SELECT event, total_waits, time_waited_micro/1e6 AS total_sec,

ROUND(time_waited_micro/total_waits/1000,2) AS avg_ms

FROM v$system_event WHERE event = 'log file sync';

Target: avg_ms < 5ms. > 20ms is a serious problem.

TECHNICAL Buffer Cache Tuning
Q7: How do you tune the Oracle buffer cache? What is cache advisory and how do you interpret it?
▼ Show Model Answer

The buffer cache is Oracle's in-memory store for data blocks. A correctly sized buffer cache dramatically reduces physical I/O.


BUFFER CACHE HIT RATIO (BCHR):

SELECT ROUND((1 - (phyrds.value / (dbget.value + consist.value))) * 100, 2) AS bchr_pct

FROM v$sysstat phyrds, v$sysstat dbget, v$sysstat consist

WHERE phyrds.name='physical reads' AND dbget.name='db block gets' AND consist.name='consistent gets';

TARGET: > 95% for OLTP. NOTE: BCHR can be misleadingly high even with large I/O — use ASH to verify.


BUFFER CACHE ADVISORY: V$DB_CACHE_ADVICE predicts physical reads at different cache sizes:

SELECT size_for_estimate MB, buffers_for_estimate, estd_physical_reads,

ROUND(estd_physical_reads * 100 / (SELECT physical_reads FROM v$sysstat WHERE name='physical reads'), 1) AS pct_reads

FROM v$db_cache_advice WHERE name='DEFAULT' AND block_size=8192

ORDER BY size_for_estimate;


INTERPRETATION: Look for the inflection point — where adding more cache stops meaningfully reducing physical reads. The optimal cache size is just past this knee in the curve.


CACHE PARTITIONING:
• DEFAULT (8K): Standard data blocks.
• KEEP: Objects that should always stay in cache (frequently accessed small lookup tables). ALTER TABLE accounts STORAGE (BUFFER_POOL KEEP);
• RECYCLE: Objects that should NOT pollute the cache (large FTS scans). ALTER TABLE audit_log STORAGE (BUFFER_POOL RECYCLE);

MULTIPLE BLOCK SIZES: If non-standard block sizes are used (16K for specific tablespaces), configure db_16k_cache_size separately.


FULL TABLE SCANS: Large FTS operations use a subset of the buffer cache (direct path read threshold) to avoid flushing frequently-used blocks. Oracle automatically uses direct path read for FTS > _SMALL_TABLE_THRESHOLD blocks. Tune with hidden parameter (carefully and with support guidance).

TECHNICAL Parallel Query Tuning
Q8: Explain Parallel Query in Oracle — when does it help, when does it hurt, and how do you tune it?
▼ Show Model Answer

Oracle Parallel Query (PQ) executes a single SQL statement using multiple parallel server processes simultaneously, splitting the work across the processes.


WHEN IT HELPS:
• Large table scans (data warehouse, analytics, reports).
• Long-running batch jobs.
• Index rebuilds, table moves, statistics gathering.
• Queries that are genuinely CPU-bound or I/O-bound with plenty of available CPUs and I/O bandwidth.

WHEN IT HURTS:
• Short OLTP queries: Parallel setup overhead exceeds execution time.
• Resource-constrained environments: Parallel query steals CPU/memory from concurrent users.
• OLTP systems: One PQ statement can consume all PQ servers, blocking others.
• Tables with poor statistics: Bad plans become catastrophic at full parallelism.

KEY PARAMETERS:
• PARALLEL_MAX_SERVERS: Maximum total parallel server processes on the instance. Set to 4–8× CPU count.
• PARALLEL_MIN_SERVERS: Pre-started servers (reduces startup overhead).
• PARALLEL_DEGREE_POLICY: MANUAL (default) | AUTO (optimizer chooses degree) | LIMITED (AUTO for star schemas only) | ADAPTIVE (12c — adjusts at runtime).
• PARALLEL_DEGREE_LIMIT: Cap on degree per statement (CPU count or specific number).
• PARALLEL_SERVERS_TARGET: Target parallel server usage before downgrade begins.

CONTROLLING PARALLELISM:
• Table-level: ALTER TABLE sales PARALLEL 8;
• Statement-level hint: SELECT /*+ PARALLEL(s,4) */ ... FROM sales s;
• Session-level: ALTER SESSION FORCE PARALLEL QUERY PARALLEL 4;
• Disable: SELECT /*+ NO_PARALLEL */ ...

RESOURCE MANAGER FOR PQ: Use consumer groups to cap parallel degree for specific user groups (e.g., developers limited to DOP=2, batch jobs allowed DOP=16).


MONITORING: V$PQ_SLAVE (active slaves), V$PQ_SESSTAT (per-session), GV$PX_SESSION (RAC-wide PQ sessions).

TECHNICAL RAC gc Wait Events
Q9: What is the Oracle wait event 'gc cr block receive time' in RAC and how do you reduce it?
▼ Show Model Answer

'gc cr block receive time' (and 'gc current block receive time') are the primary wait events in Oracle RAC environments. They represent time spent waiting for a data block from another RAC node's buffer cache via Cache Fusion over the private interconnect.


GC CR (Consistent Read) Block: Requesting node needs a read-consistent copy of a block being held by another node.

GC Current Block: Requesting node needs the current (most recent) version of a block — typically for DML.


DIAGNOSING HIGH GC WAITS:

1. Check overall gc wait profile (AWR Top Events):

SELECT event, total_waits, ROUND(time_waited_micro/1e6,1) total_sec

FROM v$system_event WHERE event LIKE 'gc %' ORDER BY time_waited_micro DESC;

TARGET: gc cr block receive time avg < 5ms, gc current < 5ms.


2. Identify hot objects causing excessive gc traffic:

SELECT o.object_name, o.object_type, p.gc_cr_blocks_received, p.gc_current_blocks_received

FROM v$segment_statistics p JOIN dba_objects o ON p.obj# = o.object_id

ORDER BY p.gc_cr_blocks_received + p.gc_current_blocks_received DESC FETCH FIRST 10 ROWS ONLY;


3. Check interconnect health:

SELECT * FROM gv$cluster_interconnects; -- verify private interconnect IP/bandwidth

oifcfg getif -- verify network classification (private vs public)


ROOT CAUSES AND FIXES:

PROBLEM: Application design — all nodes write to the same rows/blocks (hot spot):

FIX: Application partitioning — route specific business entities (accounts, customers) to specific RAC nodes. Reduces cross-node block requests dramatically.


PROBLEM: Interconnect saturation (hardware):

FIX: Upgrade to InfiniBand (56Gbps+) or 25GbE private interconnect. Verify only Oracle private traffic on interconnect (no NFS/backup traffic).


PROBLEM: Small block size causing more blocks to be requested:

FIX: Increase DB_BLOCK_SIZE (requires recreating database). Or use larger PCTFREE to fit more rows per block.


PROBLEM: Index scans on unpartitioned indexes cause nodes to request blocks from each other:

FIX: Partition indexes; use local indexes where possible; consider REVERSE KEY to distribute index inserts.

TECHNICAL Library Cache Latch
Q10: How do you identify and fix a 'latch: library cache' contention problem?
▼ Show Model Answer

LIBRARY CACHE LATCH contention occurs when many sessions compete to pin shared SQL, PL/SQL objects in the library cache — typically caused by excessive hard parsing or literal SQL (non-shared cursors).


DIAGNOSIS:

1. Confirm latch contention in V$LATCH:

SELECT name, gets, misses, ROUND(misses/gets*100,2) miss_pct, sleeps

FROM v$latch WHERE name IN ('library cache','library cache lock','library cache pin')

ORDER BY sleeps DESC;

HIGH MISS%: > 0.5% is concerning; > 1% is a problem.


2. Identify non-shared SQL (literal values causing excessive cursors):

SELECT substr(sql_text,1,80) sql_sample, count(*) cnt

FROM v$sqlarea GROUP BY substr(sql_text,1,80) HAVING count(*) > 100

ORDER BY cnt DESC;

-- Large count = same query with different literals = parse storm


3. Check parse rates vs. execute rates (AWR Load Profile):

Hard Parse / Execute < 1% is ideal. Hard Parse > 5% = problem.


ROOT CAUSES:
• Application uses literal values instead of bind variables: SELECT * FROM orders WHERE id=12345 vs id=:B1
• Dynamic SQL in PL/SQL generating different text each call.
• Very large shared pool full of non-reusable cursors.
• Many different schemas running the same package (library cache object version count).

FIXES (in priority order):

1. FIX APPLICATION: Use bind variables. This is the only proper fix. Engage developers.


2. CURSOR_SHARING=FORCE (emergency only):

ALTER SYSTEM SET CURSOR_SHARING=FORCE;

Forces Oracle to treat 'id=12345' and 'id=9999' as the same cursor by replacing literals with system-generated binds.

CAUTION: Can cause suboptimal plans (bind peeking issues); degrades performance for intentionally different queries. Use EXACT (default) in production long-term.


3. SESSION_CACHED_CURSORS: Increase per-session cursor caching (default 20). Reduces re-parse for frequently reused statements per session.


4. Open cursors: Verify applications close cursors properly — ORA-01000 or V$OPEN_CURSOR showing thousands of open cursors per session.


5. DBMS_SHARED_POOL.KEEP: Pin large frequently-used packages to prevent eviction and re-parsing.

TECHNICAL ADDM Analysis
Q12: What is Oracle's ADDM and how do you interpret its recommendations?
▼ Show Model Answer

ADDM (Automatic Database Diagnostic Monitor) is Oracle's built-in performance diagnostic engine that automatically analyzes AWR data after each snapshot and produces a findings report with prioritized recommendations.


HOW ADDM WORKS:
• MMON runs ADDM after each AWR snapshot pair.
• Analyzes DB Time consumption by wait class, top SQL, memory, I/O, segments.
• Produces ranked FINDINGS with quantified DB Time impact and specific RECOMMENDATIONs.
• Results stored in DBA_HIST_ADDM_FINDINGS and retrievable via text/HTML report.

RUNNING ADDM ON-DEMAND (for a specific snapshot range):

DECLARE l_task_name VARCHAR2(30); l_task_desc VARCHAR2(256);

BEGIN

l_task_name := 'ADDM_CUSTOM_' || TO_CHAR(SYSDATE,'YYYYMMDDHH24MISS');

DBMS_ADVISOR.CREATE_TASK('ADDM', l_task_name, task_desc=>'Custom ADDM run');

DBMS_ADVISOR.SET_TASK_PARAMETER(l_task_name, 'START_SNAPSHOT', :begin_snap);

DBMS_ADVISOR.SET_TASK_PARAMETER(l_task_name, 'END_SNAPSHOT', :end_snap);

DBMS_ADVISOR.EXECUTE_TASK(l_task_name);

END;

/

SELECT DBMS_ADVISOR.GET_TASK_REPORT(l_task_name) FROM dual;


TYPICAL ADDM FINDINGS AND MEANINGS:
• "SQL statements consuming significant database time" → Top SQL to tune (SQL IDs provided).
• "Hard parse due to literal SQL" → Implement bind variables or cursor sharing.
• "Individual database segments causing significant user I/O" → Hot table/index.
• "Buffer cache too small" → Increase db_cache_size.
• "High PGA usage causing excessive disk sorts" → Increase pga_aggregate_target.
• "Checkpoint not complete" → Increase redo log size or add redo log groups.
• "Shared pool too small" → Increase shared_pool_size.

INTERPRETING RECOMMENDATIONS:
• Each finding shows % of DB time impacted.
• Focus on top 1–3 findings — fixing the top one often reduces others.
• Not all recommendations are actionable immediately — some require application changes.
• ADDM cannot find everything — supplement with manual ASH/AWR analysis for complex issues.
TECHNICAL Cursor Pin Waits
Q13: How do you diagnose and resolve cursor contention and 'cursor: pin S wait on X' waits?
▼ Show Model Answer

'cursor: pin S wait on X' is a serious contention event where many sessions wait to pin a cursor in shared mode (read) while another session holds an exclusive pin (for hard parse or invalidation).


WHY IT OCCURS:
• A SQL statement is being hard parsed (exclusive pin held during parsing) while many other sessions want to execute the same SQL (shared pin needed).
• Triggered by: statistics gathering on a table (invalidates dependent cursors → mass re-parse), or DDL on a table (all dependent cursors invalidated).
• Also: Excessive version count — when the same SQL has too many child cursors (versions), managing them requires exclusive operations.

DIAGNOSIS:

1. Find the blocked SQL:

SELECT p1raw AS cursor_address, count(*) waiters FROM v$session

WHERE event='cursor: pin S wait on X' GROUP BY p1raw;

-- p1raw is the cursor address; join to V$SQL to find the SQL.


2. Find which SQL has high version count:

SELECT sql_id, version_count, parse_calls, sql_text

FROM v$sqlarea WHERE version_count > 100 ORDER BY version_count DESC;


3. Find child cursor invalidation reasons:

SELECT reason FROM v$sql_shared_cursor WHERE sql_id='abc123' AND child_number > 10;


RESOLUTION:
• If caused by stats gathering: Schedule stats during off-peak hours; use INCREMENTAL stats; use online stats gathering (19c).
• If caused by high version count: Investigate bind mismatch (different bind types), optimizer env differences, NLS settings per session — standardize application session parameters.
• CURSOR_SHARING=FORCE: Can INCREASE version count if it creates system-bind variations.
• DBMS_SHARED_POOL.PURGE('address,hash_value','C'): Purge specific cursor to force clean re-parse (use during off-peak with care).
• ALTER SYSTEM FLUSH SHARED_POOL: Nuclear option — flushes everything; triggers mass re-parse storm.
TECHNICAL PGA Tuning
Q14: How do you analyze and tune PGA (Program Global Area) usage?
▼ Show Model Answer

PGA holds private session data including sort areas, hash join areas, bitmap merge areas, cursor state, and session-specific variables. PGA tuning is critical for data warehouse and mixed OLTP/analytics workloads.


PGA MANAGEMENT MODES:
• PGA_AGGREGATE_TARGET (AMM disabled): Oracle automatically manages PGA for individual operations, targeting this aggregate limit.
• PGA_AGGREGATE_LIMIT (12c+): Hard cap on total PGA usage. Operations exceeding the limit are killed (ORA-04036) rather than spilling to disk. Prevents runaway PGA.
• MANUAL PGA: Setting SORT_AREA_SIZE, HASH_AREA_SIZE per session. Legacy; rarely used.

KEY METRICS:
V$PGASTAT — system-wide PGA statistics:

SELECT name, ROUND(value/1024/1024,1) MB FROM v$pgastat

WHERE name IN ('aggregate PGA target parameter','aggregate PGA auto target','total PGA inuse','total PGA allocated','maximum PGA allocated','cache hit percentage');

TARGET: PGA cache hit % > 90% (operations completed in memory without disk spill).


V$SQL_WORKAREA — per-cursor work area information:

SELECT sql_id, operation_type, policy, estimated_optimal_size/1024/1024 opt_MB,

last_memory_used/1024/1024 used_MB, last_execution

FROM v$sql_workarea ORDER BY last_memory_used DESC FETCH FIRST 10 ROWS ONLY;

LAST_EXECUTION: 'OPTIMAL' = all in memory; 'ONE PASS' = one disk spill; 'MULTI-PASS' = severe spill.


TUNING STEPS:

1. Identify sessions/SQL with MULTI-PASS executions — these need more PGA.

2. Check V$SQL_WORKAREA_ACTIVE during peak load — shows current work areas.

3. Use V$PGA_TARGET_ADVICE to model optimal PGA_AGGREGATE_TARGET:

SELECT pga_target_for_estimate/1024/1024 target_MB, estd_pga_cache_hit_percentage

FROM v$pga_target_advice;

-- Find the knee in the curve — where hit % plateaus.

4. Increase PGA_AGGREGATE_TARGET if disk spills are occurring.

5. Set PGA_AGGREGATE_LIMIT to 200% of PGA_AGGREGATE_TARGET to prevent runaway.


OLTP vs. DW: OLTP needs small PGA (short sorts); DW needs large PGA (massive hash joins, sorts over millions of rows). Size for your dominant workload.

TECHNICAL Plan Control Tools
Q15: How do you use SQL Profiles vs. SQL Patches vs. SQL Plan Baselines to control execution plans? What is the right tool for each situation?
▼ Show Model Answer

Oracle provides three mechanisms for influencing execution plans without changing SQL code:


SQL PROFILE:
• WHAT: Collection of auxiliary statistics (adjustments to the optimizer's cardinality estimates) stored in the catalog.
• HOW CREATED: SQL Tuning Advisor (automated) or DBMS_SQLTUNE.CREATE_SQL_PROFILE (manual, 12c+).
• HOW IT WORKS: Optimizer considers profile's corrected estimates when generating the plan — naturally arrives at a better plan without forcing a specific plan.
• BEST FOR: Fixing cardinality misestimation; works with Oracle's optimizer intelligence.
• PORTABLE: Yes — profile moves with the SQL (same SQL text hash).

SQL PATCH (DBMS_SQLDIAG):
• WHAT: A mechanism to inject hints into a SQL statement without modifying source code.
• HOW CREATED: DBMS_SQLDIAG.CREATE_SQL_PATCH(sql_id, hint_text, name).
• HOW IT WORKS: Oracle automatically appends the specified hints to the SQL at parse time.
• BEST FOR: Emergency plan fix when application code cannot be changed and you need to force a specific hint (use_nl, no_merge, leading, etc.).
• Example: DBMS_SQLDIAG.CREATE_SQL_PATCH('abc123def', 'USE_NL(@"SEL$1" t)', 'patch_force_nl');
• MORE SURGICAL THAN: Cursor sharing or session-level hint injection.

SQL PLAN BASELINE (SPM):
• WHAT: A set of accepted, verified execution plans for a SQL statement. Optimizer can ONLY use accepted plans.
• HOW CREATED: Captured automatically (OPTIMIZER_CAPTURE_SQL_PLAN_BASELINES) or manually loaded.
• HOW IT WORKS: Locks the plan regardless of statistics changes or parameter changes.
• BEST FOR: Plan stability across upgrades, stats changes, parameter changes.
• DRAWBACK: Must manually evolve to adopt better plans; can become stale.

DECISION MATRIX:
• Plan changing after stats gather → SQL Profile (correct cardinality) or SQL Plan Baseline (lock old plan).
• Plan changing after upgrade → SQL Plan Baseline.
• Need to inject hints without code change → SQL Patch.
• Application uses literals → fix application (then profile/baseline as interim measure).

TECHNICAL Data Pump
Q2: Explain Oracle Data Pump — expdp and impdp — advanced usage, parallelism, and troubleshooting.
▼ Show Model Answer

Data Pump is Oracle's server-side bulk data movement utility. Unlike exp/imp, Data Pump operations run on the server (the directory object must point to a server-side path).


DIRECTORY OBJECT SETUP:

CREATE DIRECTORY dp_dir AS '/oracle/datapump';

GRANT READ, WRITE ON DIRECTORY dp_dir TO dba_user;


KEY PARAMETERS:
• PARALLEL: Number of parallel worker processes. Each worker processes one table partition at a time.
• COMPRESSION: ALL | DATA_ONLY | METADATA_ONLY | NONE — compress dump file contents.
• ENCRYPTION: ALL | DATA_ONLY | METADATA_ONLY | ENCRYPTED_COLUMNS_ONLY — AES encryption of dump.
• NETWORK_LINK: Export directly from remote database to local import — no dump file created (schema migration).
• FLASHBACK_TIME / FLASHBACK_SCN: Export data as of a consistent past point (critical for consistent exports from active databases).
• TRANSFORM: SEGMENT_ATTRIBUTES:N — strip storage clauses for cross-platform migration.

ADVANCED EXPORT EXAMPLES:

-- Full database export with parallelism:

expdp "/ as sysdba" FULL=Y PARALLEL=8 DUMPFILE=full_%U.dmp LOGFILE=full_exp.log DIRECTORY=dp_dir COMPRESSION=ALL


-- Schema export with exclude:

expdp hr/hr SCHEMAS=HR,PAYROLL EXCLUDE=STATISTICS DUMPFILE=hr_%U.dmp PARALLEL=4 DIRECTORY=dp_dir


-- Table-level with query filter:

expdp hr/hr TABLES=employees QUERY=employees:'"WHERE department_id=50"' DUMPFILE=emp.dmp DIRECTORY=dp_dir


NETWORK_LINK IMPORT (no dump file):

impdp hr/hr NETWORK_LINK=source_db_link SCHEMAS=HR REMAP_SCHEMA=HR:HR_NEW PARALLEL=4 LOGFILE=imp.log DIRECTORY=dp_dir


REMAP PARAMETERS:

REMAP_SCHEMA: old_schema:new_schema

REMAP_TABLESPACE: old_ts:new_ts

REMAP_TABLE: old_name:new_name

TRANSFORM=OID:N (suppress OID for object type objects)


TROUBLESHOOTING:
• ORA-39097 (Data Pump job unexpectedly terminated): Check DBA_DATAPUMP_JOBS for stuck jobs; kill with DBMS_DATAPUMP.STOP_JOB.
• Reattach to running job: expdp attach=SYS_EXPORT_FULL_01 (job name from DBA_DATAPUMP_JOBS)
• Slow Data Pump: Check DB I/O; increase PARALLEL; ensure DEGREE set appropriately; avoid COMPRESS=ALL for very fast I/O (CPU bottleneck).
TECHNICAL SQL*Loader
Q3: How does SQL*Loader work and when would you use it over Data Pump or external tables?
▼ Show Model Answer

SQL*Loader (sqlldr) loads data from flat files (CSV, delimited, fixed-width) into Oracle tables. It runs client-side but writes directly to the database.


KEY LOADING MODES:
• CONVENTIONAL PATH: Generates redo log and runs constraints. Slow but safe for OLTP (generates UNDO, maintains all triggers/constraints).
• DIRECT PATH: Bypasses SQL engine; writes formatted data blocks directly to datafiles above the high water mark. EXTREMELY fast for bulk loads. DISABLES triggers; can defer/disable constraints.

CONTROL FILE EXAMPLE:

LOAD DATA

INFILE '/data/employees.csv'

BADFILE '/logs/employees.bad'

DISCARDFILE '/logs/employees.dis'

APPEND INTO TABLE hr.employees_stage

FIELDS TERMINATED BY ',' OPTIONALLY ENCLOSED BY '"'

TRAILING NULLCOLS

(

employee_id INTEGER EXTERNAL,

first_name CHAR,

last_name CHAR,

hire_date DATE "YYYY-MM-DD",

salary DECIMAL EXTERNAL,

dept_id INTEGER EXTERNAL,

load_timestamp EXPRESSION "SYSDATE"

)


RUN: sqlldr hr/hr CONTROL=emp.ctl LOG=emp.log DIRECT=TRUE PARALLEL=TRUE ROWS=10000


WHEN TO USE SQL*LOADER:
• Loading from flat files (CSV, fixed-width from mainframes, external vendor data feeds).
• Very fast bulk loads with DIRECT PATH.
• Transformations expressible in SQL*Loader expressions.
• Legacy ETL processes.

WHEN TO USE DATA PUMP INSTEAD: Oracle-to-Oracle data movement; schema copies; logical backups.


WHEN TO USE EXTERNAL TABLES INSTEAD:

CREATE TABLE ext_employees ORGANIZATION EXTERNAL (TYPE ORACLE_LOADER DEFAULT DIRECTORY data_dir ACCESS PARAMETERS (...) LOCATION ('employees.csv'));

External tables: Query flat files directly as if they were Oracle tables; can use INSERT INTO ... SELECT FROM ext_employees for loading; reusable for repeated loads.


PERFORMANCE TIPS: DIRECT=TRUE PARALLEL=TRUE (multiple sqlldr processes with different file splits); set ROWS=50000 to reduce commit frequency; disable indexes before load, rebuild after.

TECHNICAL LogMiner
Q4: What is Oracle LogMiner and when would you use it? How do you mine specific transactions?
▼ Show Model Answer

LogMiner (DBMS_LOGMNR) analyzes Oracle online and archived redo log files, reconstructing and presenting the DML and DDL operations as SQL statements. It's a read-only, non-invasive utility.


USE CASES:
• Auditing: What did a user do? Reconstruct unauthorized changes.
• Data recovery: Find specific deleted/updated rows when Flashback is unavailable.
• Change data capture: Base for GoldenGate's Classic Capture.
• Migration validation: Verify what changed during a migration window.
• Debugging: "When exactly did this table change and what was the before/after?"

SETUP:

-- Supplemental logging must be enabled (at minimum):

ALTER DATABASE ADD SUPPLEMENTAL LOG DATA;

-- For LogMiner to show column values: enable column logging:

ALTER TABLE hr.employees ADD SUPPLEMENTAL LOG DATA (ALL) COLUMNS;


RUNNING LOGMINER:

-- Step 1: Add log files to analyze

EXEC DBMS_LOGMNR.ADD_LOGFILE('/arch/1_5821.arc', DBMS_LOGMNR.NEW);

EXEC DBMS_LOGMNR.ADD_LOGFILE('/arch/1_5822.arc', DBMS_LOGMNR.ADDFILE);


-- Step 2: Start analysis with options

EXEC DBMS_LOGMNR.START_LOGMNR(

STARTTIME => TO_DATE('2024-03-15 14:00:00','YYYY-MM-DD HH24:MI:SS'),

ENDTIME => TO_DATE('2024-03-15 15:00:00','YYYY-MM-DD HH24:MI:SS'),

OPTIONS => DBMS_LOGMNR.DICT_FROM_ONLINE_CATALOG + DBMS_LOGMNR.CONTINUOUS_MINE + DBMS_LOGMNR.COMMITTED_DATA_ONLY

);


-- Step 3: Query the results

SELECT timestamp, operation, seg_owner, table_name,

sql_redo, sql_undo

FROM v$logmnr_contents

WHERE seg_name='EMPLOYEES' AND operation IN ('DELETE','UPDATE','INSERT')

ORDER BY timestamp;


-- Step 4: End session

EXEC DBMS_LOGMNR.END_LOGMNR;


KEY V$LOGMNR_CONTENTS COLUMNS:
• SQL_REDO: The SQL that was executed.
• SQL_UNDO: The reverse SQL (restore original state).
• SCN: System Change Number when the operation occurred.
• XID: Transaction ID (group operations in same transaction).
• ROLLBACK: Indicates if this operation was rolled back.

DICTIONARY OPTIONS: DICT_FROM_ONLINE_CATALOG (current schema) | DICT_FROM_REDO_LOGS (schema at time of redo) | DICT_FROM_EXTRACT (for GoldenGate-mode mining).

TECHNICAL SQL Trace & TKPROF
Q7: What is Oracle Trace and TKPROF — how do you trace specific sessions and interpret the output?
▼ Show Model Answer

Oracle SQL Trace generates detailed execution statistics for every SQL statement in a session — execution counts, row counts, CPU time, elapsed time, wait events, bind values. TKPROF formats the raw trace file into readable reports.


ENABLING TRACE:

Method 1 — For your own session:

ALTER SESSION SET SQL_TRACE=TRUE;

-- Or with bind variable capture and wait events (most useful):

EXEC DBMS_SESSION.SET_SQL_TRACE(sql_trace=>TRUE);

ALTER SESSION SET EVENTS '10046 TRACE NAME CONTEXT FOREVER, LEVEL 12';

-- Level 4: binds; Level 8: waits; Level 12: binds + waits


Method 2 — For another session (DBA only):

EXEC DBMS_SYSTEM.SET_EV(sid, serial#, 10046, 12, ''); -- Level 12 = binds + waits

-- Or via DBMS_MONITOR:

EXEC DBMS_MONITOR.SESSION_TRACE_ENABLE(session_id=>123, serial_num=>456, waits=>TRUE, binds=>TRUE);


Method 3 — For a database username (all sessions):

EXEC DBMS_MONITOR.CLIENT_ID_TRACE_ENABLE(client_id=>'HR_APP', waits=>TRUE, binds=>TRUE);


Method 4 — For a service:

EXEC DBMS_MONITOR.SERV_MOD_ACT_TRACE_ENABLE(service_name=>'MYAPP', waits=>TRUE, binds=>TRUE);


FINDING THE TRACE FILE:

SELECT value FROM v$diag_info WHERE name='Default Trace File'; -- current session

SELECT value FROM v$diag_info WHERE name='Diag Trace'; -- trace directory


FORMATTING WITH TKPROF:

tkprof trace_file.trc output.txt SYS=NO SORT=PRSELA,EXEELA,FCHELA EXPLAIN=hr/hr


INTERPRETING TKPROF OUTPUT:
• call: parse, execute, fetch
• count: how many times the call was made
• cpu: CPU time (seconds)
• elapsed: total elapsed time
• disk: physical reads
• query/current: logical reads (consistent/current mode)
• rows: rows processed
• Mismatched parse count vs execute: re-parsing issue (not reusing cursors)
• High disk vs query: I/O-heavy execution
• Waits section: shows specific wait events and time (with Level 8/12 trace).
TECHNICAL Statistics Management
Q8: How do you use DBMS_STATS to gather optimal statistics for large partitioned tables?
▼ Show Model Answer

Accurate statistics are the foundation of Oracle query optimization. For large partitioned tables, statistics gathering requires careful configuration to balance freshness, accuracy, and performance impact.


KEY DBMS_STATS PARAMETERS:
• ESTIMATE_PERCENT: Percentage of rows sampled. AUTO_SAMPLE_SIZE (default) is usually best — Oracle chooses dynamically based on NDV algorithm (hash-based counting, very accurate at low sample size in 11g+).
• METHOD_OPT: Controls column-level statistics and histogram creation.

'FOR ALL COLUMNS SIZE AUTO' — Oracle decides which columns need histograms based on workload.

'FOR ALL COLUMNS SIZE SKEWONLY' — Histograms only for skewed columns.

'FOR COLUMNS col1 SIZE 254, col2 SIZE 1' — Manual control.

• DEGREE: Parallel degree for stats gathering (use DBMS_STATS.DEFAULT_DEGREE or specific value).
• CASCADE: Also gather index statistics (TRUE/FALSE/DBMS_STATS.AUTO_CASCADE).
• GRANULARITY: 'AUTO' | 'PARTITION' | 'SUBPARTITION' | 'GLOBAL' | 'ALL' — for partitioned tables.

GATHERING STATS ON A LARGE PARTITIONED TABLE:

-- Gather only for partitions modified since last stats collection:

EXEC DBMS_STATS.GATHER_TABLE_STATS('HR', 'SALES', GRANULARITY=>'AUTO', INCREMENTAL=>TRUE, DEGREE=>8);


INCREMENTAL STATISTICS (11g+):
• For interval-partitioned tables: set INCREMENTAL=TRUE once.
• Partition-level synopses (small statistical summaries) stored per partition.
• On next stats gather: Only newly added/changed partitions are sampled; global stats synthesized from partition synopses.
• Massively reduces stats gather time for VLDB tables.
• EXEC DBMS_STATS.SET_TABLE_PREFS('HR','SALES','INCREMENTAL','TRUE');

LOCKING AND RESTORING STATISTICS:

-- Lock stats to prevent auto-refresh from overwriting tuned stats:

EXEC DBMS_STATS.LOCK_TABLE_STATS('HR','CRITICAL_SMALL_TABLE');


-- Restore previous statistics after a bad stats gather:

EXEC DBMS_STATS.RESTORE_TABLE_STATS('HR','SALES', AS_OF_TIMESTAMP => SYSTIMESTAMP - INTERVAL '2' HOUR);


-- Export/import stats for cross-environment migration:

EXEC DBMS_STATS.CREATE_STAT_TABLE('HR','STATS_STASH','USERS');

EXEC DBMS_STATS.EXPORT_SCHEMA_STATS('HR','STATS_STASH',NULL,'HR');

-- In target: EXEC DBMS_STATS.IMPORT_SCHEMA_STATS('HR','STATS_STASH',NULL,'HR');


MONITORING STALE STATS: SELECT owner, table_name, last_analyzed, stale_stats FROM dba_tab_statistics WHERE stale_stats='YES' AND owner NOT IN ('SYS','SYSTEM').

SCENARIO SCENARIO E: GoldenGate Replication Stopped
You are migrating a production Oracle 19c database to OCI using GoldenGate. During the migration window, the Operations team reports that GoldenGate Replicat has been in ABEND state for 2 hours. The cutover window closes in 3 hours. What do you do?
▼ Show Expert Response
IMMEDIATE TRIAGE (first 10 minutes):

1. GGSCI> VIEW REPORT REP1 — find the exact error. Common causes: ORA-00942 (table does not exist on target), ORA-01403 (no data found for key), DML conflict.

2. Check ggserr.log for full error context.

3. Check if Replicat is in discard mode: VIEW REPORT REP1; look for DISCARD FILE.


SCENARIO A — ORA-00942 (object missing on target):

• Target schema is incomplete — DDL was not replicated or failed.
• Re-run DBMS_METADATA.GET_DDL on source; create missing object on target.
• GGSCI> START REPLICAT REP1 — if error was non-fatal and replicat will retry.
• Or skip the error: GGSCI> ADD REPLICAT REP1, SPECIALRUN ..., HANDLECOLLISIONS (for initial catch-up).

SCENARIO B — DML errors (duplicate key, constraint violation):

• Likely an initial load inconsistency — some rows exist on target that shouldn't yet.
• Add HANDLECOLLISIONS to Replicat parameter: allows Replicat to ignore duplicate INSERT (treats as UPDATE) and not-found DELETE.
• Temporary measure for migration; REMOVE after catch-up and before go-live.

MANAGING THE TIME CONSTRAINT:

4. Communicate status to stakeholders immediately: estimated recovery time, impact on cutover window.

5. If Replicat cannot recover in 1 hour: consider extending cutover window or re-evaluating migration approach.

6. Decision point at T-2 hours: If lag > 5 minutes with 1 hour to cutover — extend window or roll back and try next day.


PREVENT RECURRENCE: Before any production migration cutover, run Replicat with HANDLECOLLISIONS in a test environment under load and verify zero errors for 2+ hours.

SCENARIO SCENARIO F: DataGuard Standby is 4 Hours Behind
You wake up to an alert: your DataGuard standby's apply lag is 4 hours and growing. The primary is running fine. The business requires an RPO of 30 minutes. What is your immediate response?
▼ Show Expert Response
IMMEDIATE ASSESSMENT:

1. Confirm transport lag vs. apply lag separately:

SELECT name, value FROM v$dataguard_stats WHERE name IN ('transport lag','apply lag');

If transport lag = 0 and apply lag = 4 hours → logs ARE reaching standby but MRP is slow.

If transport lag = 4 hours → logs are NOT reaching standby (network/transport problem).


CASE A — Transport lag is 0, apply lag is growing (MRP is slow):

Possible causes:
• MRP is applying a very large transaction (long-running batch, massive DML).
• Standby server is resource-constrained (CPU/I/O saturated).
• Real-time apply not enabled (using archive apply, not current logfile).

CHECKS:
• Is MRP running? SELECT process, status, sequence# FROM v$managed_standby WHERE process='MRP0';
• Server resources on standby: top, iostat, sar.
• FIX: Ensure real-time apply: ALTER DATABASE RECOVER MANAGED STANDBY DATABASE USING CURRENT LOGFILE DISCONNECT;
• Increase parallel apply (in 12.2+): ALTER DATABASE RECOVER MANAGED STANDBY DATABASE PARALLEL 4 DISCONNECT;

CASE B — Transport lag is 4+ hours (logs not arriving):

• Network outage between primary and standby.
• LGWR/LNS process on primary stopped.
• Firewall rule change blocked the connection.
• Archive log destination ERROR status.

CHECKS: V$ARCHIVE_DEST_STATUS for ERROR; ping/telnet standby TNS from primary; check if FAL server is set; check GoldenGate or DR network team.


STAKEHOLDER COMMUNICATION (critical):
• Within 15 minutes: Notify DBA manager and IT operations that RPO is breached.
• Update SLA ticket.
• Provide estimated time to recovery.
• Consider activating DR plan if standby cannot recover within SLA window.

POST-INCIDENT: Root cause analysis; implement monitoring threshold alert at 15-minute apply lag (not 30-minute RPO) to provide earlier warning.

SCENARIO SCENARIO G: Unauthorized Schema Changes in Production
The security team reports that someone made unauthorized DDL changes to the FINANCE schema in production over the weekend. The audit trail was not fully configured. How do you investigate, remediate, and prevent recurrence?
▼ Show Expert Response

1. Check existing audit trail (even partial):

2. Check alert log for DDL timestamps: grep 'ALTER TABLE\|CREATE INDEX\|DROP' $ORACLE_BASE/diag/rdbms/.../alert.log

5. Set up real-time DDL alert via OEM event or custom trigger → email/PagerDuty.

6. Conduct security review of all accounts with CREATE/ALTER/DROP privileges in production.

SCENARIO SCENARIO H: Archive Log Destination Full — Database Suspended
It is 10:30 AM on a weekday. You receive multiple alerts. The production database has suspended all user sessions (ORA-00257: archiver error). The archive log destination is full. Users cannot transact. How do you recover and what do you do in the first 10 minutes?
▼ Show Expert Response

CRITICAL: Every minute this is unresolved costs the business real money. Move fast AND methodically.


MINUTE 1–2: CONFIRM AND COMMUNICATE

• Verify: SELECT log_mode, archiver FROM v$database;
• CHECK: SELECT dest_name, status, error FROM v$archive_dest WHERE status != 'VALID';
• OPEN COMMUNICATION: Immediately notify DBA manager and operations bridge: "Production database suspended — archive log destination full. Working resolution now."

MINUTE 3–5: IMMEDIATE SPACE RELIEF

Option A — Delete old archive logs via RMAN (SAFEST):

rman target / <<EOF

CROSSCHECK ARCHIVELOG ALL;

DELETE NOPROMPT ARCHIVELOG ALL COMPLETED BEFORE 'SYSDATE - 1'; -- last 24h

EOF

Option B — If RMAN too slow and business pressure is extreme:

Emergency OS-level: identify oldest archive logs; verify they've been applied to standby AND backed up; rm oldest files.

CAUTION: Only delete what you can verify has been backed up.


MINUTE 5–8: RESUME DATABASE

• After freeing space, the archiver should auto-resume.
• Verify: SELECT status FROM v$archive_dest WHERE dest_id=1; → should return 'VALID'
• Check if sessions are reconnecting: SELECT count(*) FROM v$session WHERE status='ACTIVE';
• If archiver still suspended: ALTER SYSTEM SWITCH LOGFILE; to force an archive attempt.
• If using FRA: ALTER SYSTEM SET DB_RECOVERY_FILE_DEST_SIZE=200G SCOPE=BOTH; (temporarily increase limit if disk has space).

MINUTE 8–10: VERIFY AND STABILIZE

• Confirm users can transact.
• Run a RMAN backup of archive logs to tape/OCI to make space for local archives.
• Monitor space: SELECT round(percent_space_used,1) FROM v$recovery_file_dest;

POST-INCIDENT ACTIONS:

1. Root cause: Why did destination fill? Backup job failed? Retention policy too long? Unexpected log generation surge?

2. Increase archive log destination size (disk or FRA size parameter).

3. Fix the failed backup job that allowed logs to accumulate.

4. Implement alert at 75% and 85% FRA/archive destination usage (not 100%).

5. Add archive log backup to run every 30 minutes in cron (not just nightly).
